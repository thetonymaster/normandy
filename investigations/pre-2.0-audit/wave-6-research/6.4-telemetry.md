   `behaviours/hooks.ex:91`, is a compile-time warning and is correct.

8. **Plan acceptance wording.** "span-parenting tests for admission" can be asserted for hook spans

   which the bridge cannot parent. Asserting them needs a guard that records `:otel_tracer.current_span_ctx()` (a

9. For the 6.2 owner: the reaper's failed-start log at `resume_reaper.ex:229` already uses
   `Describe.reason_tag(reason)`, not `inspect(reason)`. Whatever `inspect` remains is elsewhere, or it was fixed in

### (1) `memory/commands.ex` logs the whole store reason, and `reason_text/1` sends inspected text to the model

- `lib/normandy/tools/memory/commands.ex:478-498`:
  ```elixir
  defp backend(reason) do
    Logger.warning(
      "memory store failure: #{inspect(reason, limit: :infinity, printable_limit: :infinity)}"
    )
    {:error, :backend, "Error: memory store unavailable: " <> reason_text(reason)}
  end
  defp reason_text(%{__exception__: true, __struct__: mod}), do: inspect(mod)
  defp reason_text({:exception, mod}) when is_atom(mod), do: inspect(mod)
  defp reason_text(reason) do  # inspect(reason) cut at @reason_chars 200
  ```
- 12 call sites of `backend(reason)`: `grep -n "backend(reason)" lib/normandy/tools/memory/commands.ex`
  (`:75, 99, 119, 161, 170, 192, 205, 231, 307, 338, 342, 381`).
- Where reasons come from: Postgres returns a raised `DBConnection.ConnectionError | Postgrex.Error` as
  `{:error, e}` (`behaviours/memory_store/postgres.ex:300-301`). A `Postgrex.Error` carries `query` (the SQL) and
  `postgres.detail`, which can quote row values such as a path or content. Store exits are wrapped as `{:exit, r}`
  (`exit_tag/1`, `:470-476`).
- What the model sees: an exception gives its module only; any other term gives up to 200 chars of `inspect`. That
  can include a string reason or a map with values.
- Tests that pin current behaviour, in `test/tools/memory_test.exs`: `:944-957` (B2: log `=~ "SELECT secret FROM
  keys"`, **must flip**), `:970-995` (a 500-char string reason is cut to 200 chars plus "…", and the log has the
  whole string, **must change**; `{:exit, :noproc}` text), `:705-733` (`"{:exit, :noproc}"` and `"ArgumentError"`
  texts), and the `:timeout` texts at `:458, 492, 504, 700, 1105`.

Options:
- **A. Tag only.** The log and the model text both use `Describe.reason_tag/1` (`components/content_block/describe.ex:20-27`:
  the exception module, a tuple's leading atom, an atom, else `type_of`). This is the smallest change, but
  `{:exit, :noproc}` becomes `:exit` for the model and in logs, so the diagnosis loses "noproc".
- **B. A safe-term describer (recommended).** A private `safe_reason/1` keeps any term built only from atoms,
  integers and tuples of those in full (`:timeout`, `{:exit, :noproc}`, `{:namespace_full, :bytes, 10}`). An
  exception is shown as its module, and for `Postgrex.Error` also its SQLSTATE `postgres.code` (an atom such as
  `:unique_violation`). Anything else falls back to `Describe.reason_tag/1`. The same text goes to the log and the
  model, and the `@reason_chars` cut goes away. Tests at `:705-733` and `:458...` stay green; B2 and `:970-995`
  flip to `refute log =~ "SELECT"` and `text == "a string (500 bytes)"`.
- **C. Keep the full log at `:debug`, use the tag at `:warning`.** This keeps debuggability, but a host running at
  debug still writes SQL and row data. It contradicts decision 6 as Wave 2 M3 read it ("logged once, value-free").

Recommendation: **B**. If wrong, operators lose the SQL text of a failing query. Postgres logs the same query
server-side, and the SQLSTATE code names the class.

### (2) `TurnError.reason` carries a credential provider's raw reason

- `server.ex:571-588` `reconstruct_config/2`: `{:token, {:error, reason}} -> {:error, {:credential_unavailable,
  cred_mod, reason}}`. `:435-436` `session_unavailable(reason)` replies `%TurnError{type: :session_unavailable,
  reason: TurnError.drop_stacktraces(reason)}`. The raw reason is kept.
- The log is already safe: `describe_reason/1` (`:421-422`) uses `Describe.reason_tag`. Nothing is persisted or
  emitted. **The only exposure is the reply** to `Turn.Server.run/2`, `Turn.Session.run/2` and `approve/2`, and
  whatever the host does with it (often an HTTP error body or a log line).
- `CredentialProvider.get_token/2 :: {:ok, String.t()} | {:error, term()}` (`behaviours/credential_provider.ex:12-13`).
  The term is the provider author's, for example a vault HTTP response, possibly with a token or a path.
- Test: `test/agents/turn/server_test.exs:1320-1330` asserts `reason: {:credential_unavailable, FailingCreds,
  :vault_sealed}`.
- The same shape applies to a session store's load reason (`session_unavailable(reason)` for a `Postgrex.Error`
  from a Postgres `SessionStore`). That is the same issue as (1) and is not listed by Q. Inventory only.

Options:
- **A. Keep it as it is (documented).** This is consistent with the Wave 2 M3 rule "full in replies" and the
  `TurnError` moduledoc ("read `:reason` for those"). The cost is that hosts must not render `:reason`.
- **B. Reduce the provider's reason in the reply (recommended).** Use `{:credential_unavailable, mod, tag}`, where
  `tag` is the term form of `Describe.reason_tag` (an atom stays an atom, a tagged tuple becomes its atom, an
  exception becomes its module), or the same `safe_reason` as (1)(B) returned as a term. The provider logs its own
  detail if it wants to. The test at `:1328` stays green (`:vault_sealed` is an atom). Add a test where the reason
  is `{:http_error, %{"token" => "SECRET"}}` and refute "SECRET" in `inspect(error)`.
- **C. Reduce every `:session_unavailable` reason** (stores too). This is wider and touches 6.2's store-failure
  work.

Recommendation: **B** now; C as a 6.2 question. If wrong, a host that pattern-matches the raw provider reason
breaks. That code is unreleased, since `:credential_unavailable` is new in 2.0 (not in 1.x).

### (3) Reaper `inspect(reason)` log: skipped (6.2 owns it; see Surprise 9).

## 4. Questions for Q

**Q1. Run totals: how usage reaches the run stop (TEL-7).**
- (a) A `:counters` accumulator carried on the transient call request (recommended; no persisted format, no handler
  contract change).
- (b) Handlers return usage beside the response, and `Turn.State` sums it. This changes `Driver.Handlers.call_llm`'s
  return, so custom AgentProcess handlers break, and it changes the persisted `Turn.State`.
- (c) Ship only `iterations`, `stop_reason` and `finish_reason`, and leave the token sum to bridges.

Cost if (a) is wrong: summary (compaction) calls are not in the run total (their llm_call span carries
`purpose: :summary`), and a custom `call_llm` reports `llm_calls: 0`. Decide also: should compaction summaries be
counted? Recommendation: no, and document it. Threading the accumulator into `Compactor`/`Summarizer` widens 6.4b.

**Q2. Turn.Server admission: under the caller (recommended) or under the run span (BaseAgent parity)?**
- Recommended: attach the caller context only, so on_prompt is a sibling of run. `metadata_test.exs:165-181`
  (Turn.Server run `:start` carries `turn_id`) keeps holding.
- Full parity: start the run span before admission. On_prompt and guardrails become run children, as in BaseAgent,
  and TEL-12's crash case is covered for free. But the run `:start` loses `turn_id` (the turn is begun after
  admission), which changes the catalogue's run-start text and that test.

Cost if wrong: a dashboard expecting on_prompt latency inside the run's duration sees it outside.

**Q3. Log level change (TEL-8) is observable behaviour.** Lifecycle start/stop go to `:debug`. Hosts that relied on
`:info` lines lose them by default. Recommendation: yes, with a MIGRATING line ("set `Logger` to `:debug` for
`Normandy.Agents.BaseAgent` or use telemetry"). Also confirm the residual `IO.warn` for `on_violation: :warn`
becomes `Logger.warning` (stderr capture in host tests would change).

**Q4. `get_response/2` (TEL-11).** Options: give it an llm_call span (recommended, non-breaking); or `@doc false`
it/remove it before 2.0 (breaking; one test caller, listed in CLAUDE.md). Cost if the span is wrong: llm_call dashboards
gain calls with no `iteration`.

**Q5. Baggage (TEL-15).** Drop inbound baggage in `A2A.Server` (recommended, a security default). Should
`AgentTool` also stop sending outbound baggage (inject trace context only)? Recommendation: keep outbound, since it
is the host's own context. Cost if wrong: a host relying on A2A baggage propagation loses it inbound. That is
breaking-ish for anyone using it with 1.x, so it needs a MIGRATING line.

**Q6. TEL-16 scope.** The audit's minimum is three events. Batch gets no span, only quieter logs. Add
`[:normandy, :batch, :run]` (span: item_count, succeeded, failed) too? Recommendation: no for 2.0. Its item runs
already emit run spans under the caller. Cost if wrong: no batch-level duration without summing.

**Q7. Wave 5 item (1), the memory backend reason.** Options A, B or C (§1b). Recommendation: B (safe-term
describer, SQLSTATE code for Postgrex). This is a behaviour change to model-facing text, so it needs a MIGRATING
note only if the memory tool's error text is considered API.

**Q8. Wave 5 item (2), the credential reason in `TurnError`.** Options A, B or C (§1b). Recommendation: B (reduce to
a tag term in the reply). Should session store load reasons get the same treatment (C, with 6.2)?

**Q9. TEL-5 scope.** Also change `guardrails.ex:189`'s `inspect(other)` (guard return contract)? Recommendation:
yes, same sub-task, same describer.
