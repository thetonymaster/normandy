## 0. Surprises

1. **The ResumeReaper `inspect(reason)` item is already fixed.** `aaf5311` ("Turn.Server,
   ResumeReaper, AgentProcess and AgentPool log error reasons by tag") changed every reaper log
   to `Describe.reason_tag/1` (`resume_reaper.ex:167, 184, 199, 229`). The failed-start log is
   `Logger.warning("ResumeReaper: failed to resume #{sid}: #{Describe.reason_tag(reason)}")`
   (`:229`). Only `inspect(sid)` remains (`:184, :199`), and that is a session id, not a reason.
   Nothing to do. decisions.md's Task 4.5–4.7 bullet is stale on this point.
2. **PERF-4 is worse than perf.md says. Measured, not estimated:** 50 concurrent
   `Turn.Supervisor.start_server/2` calls against a store whose `history/2` and
   `load_turn_state/2` each sleep 200 ms took **20 139 ms** (fully serialized: 50 × 2 × 200 ms).
   The plan's acceptance ("50 starts under 1 s") is a 20× change, not a tuning.
3. **A store failure in init is not the only init hazard. Moving the load out of `init/1` turns
   every raise in it into a restart loop unless it is caught.** Today these raise inside `init/1`.
   That makes `start_link` return `{:error, {exception, stack}}`, which Session turns into
   `:session_unavailable` (pinned by `server_errors_test.exs:165`):
   - `load_config_template(_, nil, _)` raises `ArgumentError` (`server.ex:550-555`; pinned by
     `server_test.exs:368`);
   - `ConfigTemplate.rebuild/3` raises `ArgumentError` for many template problems
     (`config_template.ex:201-238`: `translate!`, `pinned!`, `Hooks.validate_entries!`,
     `supplement_toolset!`, `validate_compaction_config!`, `validate_client_options!`, and the
     supplement's `client_builder`). Only `check_loaded/1` and `check_pinned/2` are rescued
     (`server.ex:592-609`);
   - `validate_on_approval_timeout!/1` raises for a bad saved value (`server.ex:646, 918-924`);
   - the template provider's `fetch/2` and the credential provider's `get_token/2` can raise or
     exit (`server.ex:579-581`).

   In a callback, each of these crashes the server, and the transient restart crashes it again,
   spending the restart limit that every session shares (`supervisor.ex:13-14`, 100 in 5 s). So
   the load handler must catch raise/exit/throw. Note that **`retry_load/1` already has this
   bug today**: it runs the same `load_session/3` inside `:unavailable` callbacks
   (`server.ex:442-451, 680-717`) with no catch.
4. **PERF-7: which backends actually exit.** InMemory (`Agent.*`, default 5 s:
   `in_memory.ex:48-118`) and ETS (`GenServer.call`, default 5 s: `ets.ex:61-93`) exit on a
   timeout, and every pid-backed store exits `:noproc` when its process is down. Redis does
   **not** exit on a timeout: Redix 1.5.3 returns `{:error, %Redix.ConnectionError{reason:
   :timeout}}` (`deps/redix/lib/redix.ex:149`), though it still exits on a dead connection
   process. Postgres rescues `DBConnection.ConnectionError`/`Postgrex.Error`
   (`postgres.ex:205-209`); any other Ecto raise propagates. Mnesia returns `{:aborted, _}`
   (`mnesia.ex:260-264`). Custom stores can do anything. Probe (an `append_entry` that does
   `exit({:timeout, {GenServer, :call, ...}})`): the `run/2` caller gets the exit, not a
   `TurnError`. The server crashes and restarts (`Native.whereis` then returns a new pid).
5. **A crashing Turn.Server dumps its whole `%Data{}` into the crash report**, including
   `config.memory` (the conversation), `start_opts` (a second copy of the config) and the
   handlers. Observed in the PERF-7 probe log ("State: {:idle, %Normandy.Agents.Turn.Server.Data{
   ... memory: ..., start_opts: [session_id: "s1", config: %BaseAgentConfig{...}"). The adapters
   redact the client through `defimpl Inspect` (`claudio_adapter.ex:157`,
   `openai_compatible_adapter.ex:236`), but the conversation is logged. There is no
   `format_status` anywhere in `lib/` (grep returns nothing). This is adjacent to decision 6.
   PERF-7's fix removes the most common trigger, but every other crash still dumps the
   conversation. See Q5.
6. **B2 is small in CPU and moderate in memory.** Measured for one copy of the `%Data{}`
   `spawn_task` captures. Messages are ~2 KB, and binaries over 64 B are refc and not copied:

   | messages | flat heap per copy | spawn+copy time | same, memory entries stripped |
   |---|---|---|---|
   | 50 | 29 KiB | 4 µs | ~0 µs |
   | 200 | 105 KiB | 33 µs | 1 µs |
   | 1000 | 513 KiB | 137 µs | ~0 µs |

   The copy loses sharing: 24 043 words shared become ~65 k words flat at 1000 messages, 2.7×.
   Against LLM latency this is noise. What matters is transient heap: one copy per worker, plus
   one per tool task (`Task.async_stream` closes over `config`), i.e. N+1 copies per batch. Size
   B2 as a small task, not a throughput item.
7. **`:sys.get_state/1` right after `start_link` already sees the post-load state when the load
   is an inserted `{:next_event, :internal, :load}`.** Probe: a gen_statem whose init returns
   `[{:next_event, :internal, :load}]` and whose load handler sleeps 300 ms; `:sys.get_state`
   right after `start_link` returned `{:idle, :loaded}`. gen_statem runs inserted events before
   it receives any message, system messages included. So the ~18 `:sys.get_state` assertions in
   `server_test.exs`/`server_hooks_test.exs` (e.g. `server_test.exs:2539, 2580`,
   `server_hooks_test.exs:147, 565, 651, 683`) keep working unchanged, and no turn call can
   arrive "during loading". `:postpone` is not needed.
8. **`gen_statem` init `{:stop, {:already_started, pid}}` gives the shape `Turn.Start` already
   accepts, with no crash log.** Probe under a DynamicSupervisor: `start_child` returned
   `{:error, {:already_started, pid}}`, and the captured log was 0 bytes. `Turn.Start` maps the
   bare shape to `{:ok, pid}` (`start.ex:26-27, 53`). This is the cheap fix for the
   `register_self` `:taken` leftover.
9. **The passivation timer is a `state_timeout`, so calls that keep the state don't reset it.**
   `idle_timeout/1` is `{:state_timeout, ms, :passivate}` (`server.ex:1559`). A rejected input
   (`{:keep_state, data}`, `server.ex:737, 743`) leaves the timer running from the last `:idle`
   entry, so a session receiving only rejected inputs passivates on schedule. This is minor and
   widens the passivation window below.
10. **The `server_tool_use` repair is blocked on an API fact nobody has verified.** The bundled
    Claude API docs describe only the continuation (send the paused turn back with no extra user
    message: `claude-api/shared/tool-use-concepts.md:132`). They say nothing about a paused turn
    followed by a new user message. Wave 6 cannot settle this offline (Q6).

## 4. Deferred: Turn.Server compaction is not persisted

### Current behaviour
- `{task_ref, {:compact_result, config2, meta}}` (`server.ex:779-789`) adopts `config2` (the
  compacted memory) in the process only. Nothing is written to the store.
- Every start rebuilds memory with `AgentMemory.from_entries(history)`
  (`server.ex:615-626`; `agent_memory.ex:341-352`). That is the full uncompacted chain.
- The second reader of the store history is `AgentProcess.reconstruct_agent/1`
  (`agent_process.ex:795-817`, `get_agent` in `:server` mode).
- Compaction keeps each kept entry's id but **strips thinking from kept messages**
  (MIGRATING-2.0.md:1144-1147). So a compacted memory is not a subset of the stored entries:
  kept entries have the same ids and different content. A summary entry and `after_compact`
  injections get new ids.
- The MIGRATING note is in place (`MIGRATING-2.0.md:1148-1157`, "a later 2.0 release stores
  compaction").
- `SessionStore` callbacks (`behaviours/session_store.ex:35-55`): `append_entry`, `history`,
  `fork`, `save/load_turn_state`, `save/load_config_template`, `list_resumable`. There is no
  snapshot or replace operation. Five backends, plus the shared contract
  `test/support/session_store_contract.ex`.

### Tests that pin today's non-persistence (they change with any fix)
- `server_hooks_test.exs:457` "after a restart, after_compact reports the dropped messages again
  under the same ids". With persistence, the restarted server starts compacted, so nothing
  would be dropped again.
- `server_hooks_test.exs:503` "after_compact gets dropped entries under their store ids;
  injections stay out of the store" (`refute Enum.any?(stored, &(&1.content == "remember: metric"))`).
  A snapshot would carry the injection, so the test's intent changes.
- `server_test.exs:173, 1169` compact on the live server only; they stay valid.

### Paths
Only Turn.Server persists, so only the Server writes compaction. Both readers
(`Turn.Server.with_stored_memory/3` and `AgentProcess.reconstruct_agent/1`) go through
`AgentMemory.from_entries/1`. Driver, Inline, BaseAgent and `stream/3` hold memory only in the
returned config, so nothing changes there.

## 7. July leftovers in Turn.Server

### `register_self` discards `{:error, :taken}`
- `server.ex:359` calls `register_self/1` and ignores the result; `:1563-1568`.
  `SessionRegistry.register/3 :: :ok | {:error, :taken}` (`session_registry.ex:17`). Only
  self-registering registries reach it: Native (`native.ex:59-64, 87`) and custom ones without
  `child_name/2`. Horde and Redis use `:via` (`horde.ex:127`, `redis.ex:85-86`).
- The documented behaviour (`session.ex` moduledoc, "Start-time race") is that a losing
  duplicate keeps running unregistered and writes into the same session (July audit,
  performance-race-audit.md:146-148).
- No test pins the loser running.

### Passivation window
- `Session.run/2` → `Server.run(pid, input)` (`session.ex:233-235`), which is
  `:gen_statem.call(..., :infinity)` (`server.ex:337-338`). There is no catch.
- A server stops `:normal` only on `:passivate` in `:idle`/`:unavailable`
  (`server.ex:870-877`). That is the only `{:stop, :normal, _}` in the file: grep
  `{:stop,` gives 1 hit. So a caller whose call races passivation gets
  `exit {:normal, {:gen_statem, :call, _}}`, or `{:noproc, _}` when the pid is already dead. In
  both cases the turn never started: calls queued behind a processed `:passivate` are never
  handled, and nothing is pending in those states.
- `AgentProcess` `:server` mode inherits the race (`agent_process.ex:649, 708`).
- No test covers it.

## Proposed approach

### A. PERF-4: load after `init/1` (`Turn.Server`)
1. `init/1` keeps only the pure checks plus registration:
   - the `:config` / `:template_provider` presence check moves out of `load_config_template/3`
     into `init/1`, still raising `ArgumentError` (keeps `server_test.exs:368` and a fast
     failure for a misconfigured start);
   - `register_self/1` (see F);
   - then `{:ok, :loading, %Data{session_id, store, registry, start_opts: opts, idle_timeout_ms},
     [{:next_event, :internal, :load}]}`.
2. New clause `handle_event(:internal, :load, :loading, data)`:
   `safe_load(opts)` → on `{:ok, ...}` it does what init does today, as a transition (`init_data`
   → `with_session_start`, converted to `{:next_state, :idle, data, actions}`, as `retry_load/1`
   already does at `:446-449`, keeping the `:session_start`/`:resume` next events). On
   `{:error, reason}` it does `unavailable_data/2` → `{:next_state, :unavailable, ...}`.
3. `safe_load/1` wraps `load_session/3` in `try ... catch kind, reason ->` and returns
   `{:error, {:load_crashed, normalized}}`. `normalized` is
   `Exception.normalize(kind, reason, stacktrace) |> TurnError.drop_stacktraces()`, as in
   `handler_crash/5` (`:1517-1527`). Log it once, by tag (`describe_reason/1` gains a clause; a
   raised bug logs `TurnError.format_raised/3`, arities only). `retry_load/1` uses the same
   wrapper, which fixes Surprise 3's existing crash. Also map
   `validate_on_approval_timeout!/1`'s raise into `{:invalid_template, msg}`, consistent with
   `check_template/1`.
   - Reply shape for `server_errors_test.exs:165`: keep `reason: %ArgumentError{}` if
     `session_unavailable/1` unwraps `{:load_crashed, e}` to `e`. Otherwise update the test to
     `reason: {:load_crashed, %ArgumentError{}}`. Q3.

### B. PERF-7: store calls never crash the server
1. One private helper in `Turn.Server`:
   ```elixir
   # A store that exits (a GenServer/Agent call timeout, a dead store process) fails the
   # write like an {:error, reason} does; a raise is a bug and still raises (decision 15c).
   defp store_call(fun) do
     fun.()
   catch
     :exit, reason -> {:error, {:store_exit, TurnError.drop_stacktraces(reason)}}
   end
   ```
   Wrap `append_to_store/5` (`:1590`), `persist_turn_state/2` (`:1578`) and, through
   `safe_load/1` (A3), every load. The exit then feeds the existing
   `fail(data, {:persist_failed, reason})` and `:unavailable` paths. `{:finalize}`/`{:fail}`
   best-effort persists (`:1322, :1330`) become truly best-effort. Persisted `TurnError` reasons
   already strip a call's args (`TurnError.redact`, `242a864`). `describe_reason/1` logs
   `{:store_exit, r}` by tag.
2. Reply: `{:error, %TurnError{type: :persist_failed, reason: {:store_exit, reason}}}`. The
   `:store_exit` wrapper lets a host tell a timeout from a store's own `{:error, _}`. Raises:
   Q4.
3. **Acceptance "a store timeout doesn't restart the server":** a fake store whose
   `append_entry/3` does `exit({:timeout, {GenServer, :call, [:store, :append, 5000]}})` when an
   atomics flag is set. This is deterministic and needs no 5 s wait. Under
   `Turn.Supervisor.start_link(max_restarts: 0)` (so any restart would kill the supervisor), the
   test asserts that `Turn.Server.run/2` returns
   `{:error, %TurnError{type: :persist_failed, reason: {:store_exit, {:timeout, _}}}}`,
   `Process.alive?(srv)`, `Process.alive?(sup)`, and `Native.whereis(reg, sid) == {:ok, srv}`
   (same pid). It also asserts the persisted turn state holds no stacktrace (reuse
   `contains_stacktrace?` from `server_errors_test.exs`). One more case for a `save_turn_state`
   exit during `{:finalize}`: the reply is still `{:ok, _}`. One for an `:unavailable` retry
   whose `history/2` exits: the server stays `:unavailable`. A realistic variant with
   `:sys.suspend/1` on the InMemory Agent would cost 5 s, so it isn't recommended.

### D. Compaction persistence (deferred from Wave 5)
Recommended: **a snapshot entry in the existing history stream**. It needs no new store callback,
so all 5 backends and custom stores keep working unchanged.
1. When `{:compact_result, config2, meta}` has `meta.compacted == true`, the server appends one

   `from_entries/1`.

   store") or log, emit nothing new, and continue (today's behaviour on restart). Q7.

## Questions for Q

**Q1. B2 on the sync BaseAgent path.** BaseAgent classifies inside each tool task, so a slim
config there also changes what `PolicyEngine.check/2`'s `ctx.config` sees.
(a) Slim only Turn.Server's tool tasks (classify stays in the worker with the full config).
BaseAgent is unchanged.
(b) Also move BaseAgent's classify out of the tasks (sequential policy checks, then parallel
execution).
(c) Give policy engines a memory without entries everywhere (breaking).
*Recommend (a).* Turn.Server is where large, long-lived histories live, and the measured cost is
small (Surprise 6). Cost if wrong: BaseAgent keeps N copies per batch, ~137 µs and 0.5 MiB each
at 1000 messages.

**Q2. Timing acceptance on CI.** Keep the literal "< 1 s" wall-clock test in the default suite
(5× headroom, `async: false`), or tag it `:perf` and rely on the deterministic gated test for
the gate? *Recommend default suite plus the gated test.* Cost if wrong: an occasional CI flake on
an overloaded runner.

**Q3. Reply shape for a crash during the load.** `{:load_crashed, %ArgumentError{}}`, or the
bare exception as today's `server_errors_test.exs:165` expects? *Recommend the bare normalized
exception* (no tagged tuple in replies, decision 15b). The log says it crashed. Cost if wrong:
hosts can't tell "provider raised" from "provider returned this exception" in the reason.

**Q4. PERF-7 scope.** Catch only `:exit` (timeouts, dead store) and let raises crash
(decision 15c: bugs raise), or catch raises from stores too? *Recommend exits only for in-turn
writes; everything during the load* (where a crash means a restart loop). Cost if wrong: a
buggy custom store that raises mid-turn still spends the shared restart budget.

**Q5. Crash reports dump the conversation (Surprise 5).** Add `format_status/1` to Turn.Server
(OTP 25+; the minimum supported Elixir 1.15 needs OTP ≥ 24, so it needs a guard or the
`format_status/2` fallback) that shows ids and state names only? It is not in plan.md's 6.2 text.
*Recommend yes, in 6.2a* (~30 lines). Otherwise route it to Task 6.4. Cost if skipped:
conversation content (PII) in error logs on every remaining crash path.

**Q6. `server_tool_use` after a failed pause.** (a) Live probe in Task 7.6 first, fix only if
the API rejects it. (b) Pre-emptively continue a paused turn before admitting the next input
(an extra LLM call). (c) Strip unmatched server blocks on the wire (edits history, which breaks
the append-only rule). *Recommend (a).* Cost if wrong: one failed request (400) for a session
after a rare pause-then-crash, until fixed.

**Q7. Compaction persistence (persisted-format change).** (a) A snapshot entry (`role:
"compaction"`) in the history stream, applied by `from_entries/1`: no store callback change, but
`history/2` readers see a new role. (b) A new optional `SessionStore` callback
(`save_snapshot/3`, `load_snapshot/2`) on all 5 backends with a contract suite (bigger; a
Postgres column or table). (c) Keep the known limit for 2.0 (the MIGRATING note stays).
Sub-question: does a failed snapshot write fail the turn (`:persist_failed`) or log and continue
uncompacted on restart? *Recommend (a) with log-and-continue.* A failed snapshot only degrades to
today's behaviour. Failing a turn whose messages are all stored would be a worse outcome. Cost if
wrong: (a) is a format that later readers (and 2.x) must keep understanding.

**Q8. Duplicate start under a self-registering registry.** The losing start now returns
`{:error, {:already_started, pid}}` from `Turn.Server.start_link/1` and `Turn.Supervisor.start_server/2`
(`Turn.Session` and `ResumeReaper` handle it already) instead of a running unregistered
duplicate. This is a behaviour change for anyone calling `start_server/2` directly. *Recommend
yes,* with a MIGRATING line. Cost if wrong: a direct caller that pattern-matched `{:ok, _}` on a
racing second start now sees an error tuple.

**Q9. ResumeReaper concurrency knob.** A module attribute (16), or a new
`:max_concurrency` start option (public, NimbleOptions-validated, documented)? *Recommend the
attribute.* Cost if wrong: a deployment with a slow store can't lower the burst without a
code change.
