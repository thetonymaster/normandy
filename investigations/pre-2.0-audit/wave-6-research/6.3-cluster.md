Scope: PERF-6, PERF-8, PERF-10, PERF-12, B5, and the July Redis/store leftovers (Redis fork id,
Redis pipeline in-band errors, plus the July store items still open). Everything below was checked
against HEAD `d624fbf` on 2026-10-06. Probes ran against the already-running local test Redis
(`normandy-test-redis`, loopback, no replicas). Each probe used its own namespace and deleted its keys

Plan text (plan.md:740): "the Redis registry resolves `whereis` without the GenServer hop; the

## 0. Surprises

1. **PERF-12's fix, as worded, would silently break the fail-closed guarantee.** Redis's `WAIT`
   "blocks the current client until all the previous write commands **[of that client]** are
   successfully transferred and acknowledged" (Redis docs; in the server source the offset waited on
   is `c->woff`, the replication offset of that client's last write). A `WAIT` sent on a dedicated
   connection that did not itself do the write waits for nothing. It would return as soon as the
   replicas reach that connection's own offset, which is 0 for a connection that never wrote.
   So "`WAIT` runs on its own connection" (plan.md:740) only works if **the write and its `WAIT` go
   together** on a connection that is not shared. This is documented Redis behaviour; I could not
   check it locally because the test Redis has no replica (`INFO replication`: `role:master
   connected_slaves:0`).
2. **The Redis combo cannot separate connections today, although the guide says it can.**
   `Cluster.redis_child_specs/1` starts one Redix connection. It gives that connection to the
   registry (`cluster.ex:184`) and also builds the store handle on it as `{conn_name, ns}`
   (`cluster.ex:196`). There is no option for a second connection. Yet
   `docs/guides/distributed_sessions.md:232` says "give the registry its own connection (pass a
   separate `:conn`)". On top of that, the combo's store handle has no `wait` element, so
   `config :normandy, :redis_wait` applies to it (`session_store/redis.ex:208-213`): set that app
   env and every `WAIT` runs on the one connection the registry also uses.
3. **Wave 5.4b made ETS, Mnesia and InMemory scan the whole namespace on every `put`.**
   `Docs.put/5` calls `totals(docs)`, a reduce over every document (`memory_store/docs.ex:27-34,
   86-88`, comment: "The whole namespace is in hand, so its totals are exact: no counter to keep").
   Once the store keeps one row per document (PERF-10), that is no longer true. ETS and Mnesia then
   need a per-namespace counter row, updated in the same serialized step as the write. Without it,
   either the limits break or every put scans all rows again. The shared contract already pins
   this behaviour (`memory_store_contract.ex:212-347`, "put/6 limits"), so it will catch a
   regression.
4. **What has been released, and so what counts as breaking:**
   - **MemoryStore is unreleased.** It is not in v1.3.0
     (`git ls-tree v1.3.0` lists no `memory_store*`). Changing the ETS/Mnesia row layout therefore
     needs no data migration and no MIGRATING entry. One test pins the old Mnesia attributes:
     `test/behaviours/memory_store/mnesia_test.exs:35` (`[:namespace, :docs]`).
   - **SessionStore, SessionRegistry.Redis and ResumeReaper are released** (all are in v1.3.0).
     So a new or changed `SessionStore` callback, or a new Redis registry handle shape, breaks
     third-party stores and hosts. That makes them questions for Q.
5. **"Prune the eager set when the session reaches a terminal state" does not fit how sessions
   work.** `:stopped` and `:failed` are per-turn states: an eager session sits in `:stopped`
   between turns and becomes resumable again when its next turn starts. So the index can't simply
   drop sessions. It has to be "eager sessions whose turn is in flight", switched on and off as
   the turn state is persisted. Also, the plan's acceptance ("the eager set shrinks after a
   session is **deleted**") only tests the delete half.
6. **Deleting a session is not simple on Postgres and Mnesia.** On those two backends, forks share
   ancestor entries (a global parent-linked forest: `session_store/postgres.ex:8-9, 104-110`;
   `session_store/mnesia.ex:149-152`). Deleting a session's chain would break its forks' history.
   Mnesia would even abort the fork's reads with `{:broken_chain, id}` (`mnesia.ex:243-246`).
   On InMemory, ETS and Redis, a fork copies the history, so deleting is trivial there.
7. **Postgres `list_resumable` has no index.** `MigrationAddResumePolicy` adds the `resume_policy`
   column only (`postgres/migration_add_resume_policy.ex`), so `WHERE resume_policy = 'eager'`
   (`postgres.ex:181-189`) scans the whole `normandy_sessions` table on every `:nodedown`. Mnesia's
   `list_resumable` is a `foldl` over the whole sessions table inside a transaction
   (`mnesia.ex:204-216`). ETS's is a `match_object` that copies every template (`ets.ex:168-178`).
8. **Already fixed, or owned by another group:**
   - Fixed: Redis `whereis` now maps a transport error to `{:error, reason}`, not `:none`
     (`session_registry/redis.ex:204-206`). That was a July MEDIUM item.
   - Fixed: the ResumeReaper's failed-start log names the reason by tag
     (`resume_reaper.ex:229`). This was a Wave 4.5–4.7 deferred item (decisions.md:41).
   - Still present, in the perf.md §A "Still present" list, but not Redis/store items
     (I assume they belong to 6.5):
     - `register_self` drops `{:error, :taken}` (`turn/server.ex:1563-1568`).
     - `Session.run` does not retry on `:noproc` (`turn/session.ex:232-236`).
9. **Measured baselines (loopback Redis, RTT about 0.1 ms; production RTTs are higher):**
   - **Registry lookups:** `whereis` through the owner GenServer manages about 9.5k lookups/s.
     A direct `GET` on the same shared Redix connection manages about 122k/s.
   - **Registry refresh:** one `:refresh` over 5,000 sessions holds back a `whereis` for 604 ms.
     A pipelined `EVALSHA` refresh of the same 5,000 keys takes 14 ms.
   - **`WAIT` on the shared connection:** a registry `whereis` issued while 5 appends run with
     `wait: {1, 100}` returned after 622 ms. It was serialized behind every `WAIT`.

## 1. PERF-6 — Redis SessionRegistry: GenServer hop, sync I/O, sequential refresh

### Current behaviour (verified)

`lib/normandy/behaviours/session_registry/redis.ex`:
- `whereis/2` makes a `GenServer.call` to the per-node owner, with the default 5 s timeout
  (`:75-76`):
  ```elixir
  def whereis(owner, session_id), do: GenServer.call(owner, {:whereis, session_id})
  ```
  The owner then runs a blocking `Redix.command(s.conn, ["GET", key])` (`:192-210`). A stale value
  makes it delete the key from inside the owner (`stale/3`, `:267-270`).
- `register/3` and `unregister/2` are owner calls (`:78-82, 172-225`). They have to be: the owner
  monitors the registered pids and deletes their keys on `:DOWN` (`:227-240`).
- Refresh (`:242-248`) walks every session one at a time, sending one `EVAL` each:
  ```elixir
  def handle_info(:refresh, s) do
    Enum.each(s.sids, fn {sid, {pid, _ref}} ->
      pexpire_if_owner(s.conn, reg_key(s.ns, sid), :erlang.term_to_binary(pid), s.ttl)
    end)
  ```
  - It uses `EVAL` with the full script text, never `EVALSHA` (`:286-288`).
  - It ignores the return value. A `0` (we no longer own the key) is dropped.
  - The interval is `ttl/2` (`:166-167`), and the default TTL is 60 s (`:22`).
- `Via.whereis_name/1` and `Via.send/2` go through `Reg.whereis` too, so they also make the hop
  (`session_registry/redis/via.ex:28-53`). `Via.register_name/2` makes the `register` call
  (`:11-26`).
- The handle is the owner's registered atom (`:11`, "The `handle` is the owner's registered
  name"). The connection and namespace live only in the owner's state (`:169`).

## 2. PERF-8 — The eager-resume set and session data grow forever

### Current behaviour (verified)

- **The behaviour has no delete or expiry callback.** `session_store.ex:35-55` has 8 callbacks:
  append_entry, history, fork, save/load_turn_state, save/load_config_template, list_resumable.
  `list_resumable/1` is documented as "eager sessions regardless of their turn state" (`:48-55`).
- **How each backend tracks the eager set:**
  - **Redis:** `save_config_template/3` runs `SADD` for an eager template and `SREM` otherwise,
    and that is the only time a session ever leaves the set (`session_store/redis.ex:162-173`).
    `list_resumable` is `SMEMBERS` (`:187-195`), O(N) and blocking on the server.
  - **Postgres:** `list_resumable` filters on the `resume_policy` column (`postgres.ex:181-189`).
    That column has no index (see Surprise 7).
  - **Mnesia:** `foldl` over the whole sessions table inside a transaction (`mnesia.ex:204-216`).
  - **ETS:** `match_object` over `{{:config_template, :_}, :_}`, which copies every template into
    the owner (`ets.ex:168-178`).
  - **InMemory:** a comprehension over every template (`in_memory.ex:116-127`).
- **The reap is serial.** On each `:nodedown`, `ResumeReaper.reap/1` (`resume_reaper.ex:150-170`)
  calls `list_resumable`, then for **each** id makes a synchronous `whereis`
  (`not_running?/3`, `:174-189`) and a `load_turn_state` (`non_terminal?/3`, `:191-207`). It then
  starts the session synchronously (`start_session/2`, `:209-236`), and `Turn.Start` can retry it
  20 times × 10 ms (`turn/start.ex:18, 29-37`). All of this runs one id after another inside the
  reaper GenServer. Decision 21's bullet (decisions.md:41) defers "`reap/1` is synchronous (~200 ms
  per session while a registry converges)" to Wave 6.
- **Where turn states are persisted** (`turn/server.ex`):
  - `{:persist, ts}` at `:1260-1264` (a failure fails the turn).
  - The terminal persist at `{:finalize, _}`, `:1319-1322`. Best effort: `_ = persist_turn_state`.
  - The terminal persist at `{:fail, _}`, `:1328-1330`. Also best effort.
  - The function itself, `persist_turn_state/2`, at `:1576-1579`.
  - The server already knows `data.resume_policy` (`:480-495`) and has
    `resumable?/1 = status not in [:stopped, :failed]` (`:662-663`).
- **Turn.Driver and Turn.Inline do not touch the store.** Their `{:persist, _}` is a no-op
  (`turn/driver.ex:84-86`, `turn/inline.ex:110-112`). The BaseAgent `run/3` and `stream/3` paths
  have no store either. **Turn.Server is the only writer of turn state.**
- **Where config templates are saved:** only `Turn.Session.save_template/2`
  (`turn/session.ex:371-379`). It runs on a Tier-2 start with a `:config` (`:368-369`).
- **AgentProcess** (`:server` mode) reads history only (`coordination/agent_process.ex:801`). It
  creates an InMemory store per agent when none is given (`:460`).
- **ETS, InMemory and Mnesia SessionStores keep every conversation in RAM with no way to remove
  it.** No public function deletes a session from any store. The only deletes in the codebase are
  the MemoryStore's `delete_namespace` and the coordination contexts
  (`grep -rn "delete_session\|def delete\b" lib`).

## 3. PERF-10 — MemoryStore ETS/Mnesia: one row per namespace

### Current behaviour (verified)

- **ETS** (`memory_store/ets.ex`):
  - The moduledoc says "One row per namespace, `{namespace, docs}`" (`:3-5`). The table is a
    `:set, :protected, read_concurrency: true` table (`:58-59`).
  - Reads (`list/3`, `get/3`) look up the whole namespace map in the caller (`:31-35, 75-80`):
    ```elixir
    def get({_pid, table}, ns, path), do: Docs.get(docs(table, ns), path)
    ```
  - Writes go through the owner: `{:apply, ns, fun, args}` copies the namespace out, runs `Docs`,
    and re-inserts the whole map (`:64-68`).
  - The handle is `{owner_pid, tid}` (`:24-29`).
- **Mnesia** (`memory_store/mnesia.ex`):
  - The record is `{table, ns, docs}`, with attributes `[:namespace, :docs]` (`:80`), created by
    `MnesiaSetup.create_table!/4`, which always uses `{:type, :set}` (`mnesia_setup.ex:29-40`).
  - Every read is a transaction that reads the whole row (`:113, 123-128`).
  - Every write takes a write lock on the namespace row and writes the whole map back (`:115-121`).
    With `disc_copies`, each write logs the whole namespace to every replica.
- **InMemory** (`memory_store/in_memory.ex`) is one `Agent` whose state is `%{ns => docs}`. The
  data never leaves the process heap, so the copying problem does not apply. It shares `Docs` with
  ETS and Mnesia.
- **Interaction with Wave 5.4b:** `Docs.put/5` computes `totals(docs)` with a reduce over every
  document before each write (`docs.ex:27-39, 86-93`). That is cheap today only because the whole
  map is already loaded. The behaviour requires the limit check to be atomic with the write and
  to count every document past the list limit (`memory_store.ex:25-36`). The other backends keep
  counters:
  - Postgres has a counter table, `normandy_memory_namespaces` (CLAUDE.md:100).
  - Redis has a `:bytes` key plus its index (`memory_store/redis.ex:241, 270-271`).
- **The memory tool's store calls per command** (`tools/memory/commands.ex`):
  - `create`: `not_directory` does a `list` (`:298-308`), `not_under_file` does one `get` per
    ancestor (`:368-382`), then the `put` (`:110`). That is 2 + depth calls, and on ETS/Mnesia
    each one copies the namespace.
  - `str_replace` and `insert`: a `get`, then a CAS `put` (`:200, 211`).
  - The memory tool already catches store exits and raises (`commands.ex:462-468`).

### Tests that pin current behaviour

- Contract `test/support/memory_store_contract.ex`: about 33 tests (`:25-430`). They include the
  put/6 limits block (`:212-354`) and three concurrency tests through the memory tool
  (`:356-430`). The contract runs on:
  - `memory_store/in_memory_test.exs` and `ets_test.exs`
  - `mnesia_test.exs` (untagged, `async: false`, resets Mnesia per test)
  - `redis_test.exs` (`:redis`) and `postgres_test.exs` (`:postgres`)
- `test/behaviours/memory_store/mnesia_test.exs:35` asserts
  `:mnesia.table_info(:normandy_memory_documents, :attributes) == [:namespace, :docs]`.
  **This test will change.**
- `test/tools/memory_test.exs:704-730` pins two things:
  - The ETS handle shape: `{ets_pid, _table} = ets = MemoryStore.ETS.new()`.
  - That a direct read on a dead owner's table raises `ArgumentError`, reported as `"Error: memory
    store unavailable: ArgumentError"`.

  Keep both: the handle stays `{pid, tid}`, and reads stay direct.
- `test/options/store_options_test.exs:7, 9` checks the `new/1` options of
  `MemoryStore.ETS` and `MemoryStore.Mnesia`.
- `test/behaviours/memory_store/docs_test.exs` covers the pure `Docs` functions. Docs stays in
  place for InMemory.

## 4. PERF-12 — Redis SessionStore `WAIT` stalls the shared connection

### Current behaviour (verified)

`lib/normandy/behaviours/session_store/redis.ex`:
- **Where `WAIT` runs:** `append_entry` (`:84-96`), `save_turn_state` (`:130-138`) and
  `save_config_template` (`:152-174`) each call `wait(conn, wait)` after the write, on the **same**
  connection (`:230-238`). That shared connection is where `WAIT` blocks every later pipelined
  command.
- **Where the setting comes from:** the handle `{conn, ns, {n, t}}`, otherwise
  `config :normandy, :redis_wait`, otherwise `{0, 0}` (`:204-213`).
- **What is already guarded:** `check_wait!/2` already rejects `t = 0` when there are replicas
  (`:215-228`). A positive `t` still blocks the connection for up to `t` ms per write.
- **The docs already know:** the moduledoc names the problem: "Redis treats 0 as wait forever,
  which would stall the shared connection" (`:21-23`).
- **`new/1` opens its own Redix connection** (`:74`), so a handle from `new/1` is not shared. The
  problem appears when the host passes a shared connection. That is what the Redis combo does
  (Surprise 2).

### Tests that pin current behaviour

- `test/behaviours/session_store/redis_wait_test.exs:17-35` (`:redis`). `new(wait: {1, 50})`
  stores the wait in the handle (`{_conn, _ns, {1, 50}}`), and writes return
  `{:error, {:wait_unmet, 0, 1}}`.
- `redis_backend_error_test.exs:35, 41` (untagged):
  - `new/1` rejects a replica wait with no timeout.
  - A bad app env raises on the write.
- `redis_store_extra_test.exs:31` (`:redis`): `WAIT` with 0 replicas is a no-op.

### Baseline (probe)

- `probe_redis.exs`: 5 tasks append with handle `{conn, ns, {1, 100}}` on the conn the registry
  owner uses. A `whereis` issued 5 ms later returned after **622 ms**, about 5 × 100 ms plus the
  queue.
- `probe_unblock.exs`:
  - While one connection is blocked in `WAIT 1 10000`, a `PING` on **another** connection
    returns in 197 µs, and the waiting task is still pending.
  - `CLIENT UNBLOCK <id>` releases the `WAIT` in 2 ms, with `WAIT` returning `{:ok, 0}`.

  This gives a deterministic test with no sleeps (see Proposed approach).

## 5. B5 — ETS SessionStore copies the whole memory on every append

### Current behaviour (verified)

`lib/normandy/behaviours/session_store/ets.ex`:
- **The table and handle:** the table is `[:set, :private]` (`:97-101`), and every operation is a
  `GenServer.call` to the owner (`:59-93`). The handle is the owner pid (`:52-57`).

- **History is O(n) by nature.** `history` runs `AgentMemory.entry_chain/1` on the looked-up
  memory (`:113-115`).
- **The only caller is Turn.Server.** It calls `append_entry` once per message
  (`append_to_store/5`, `turn/server.ex:1584-1597`; the call site is the `append` effect at
  `:1250-1257`), and `history` once at start (`with_stored_memory`, `:616`). AgentProcess calls

## Proposed approach

### PERF-6: caller-side `whereis` and a batched refresh

1. **`whereis/2` runs in the caller.** It does a `GET` on the registry's Redix connection, then
   `decode_pid/1` (unchanged, `[:safe]`). The stale branch also runs in the caller
   (`del_if_owner` via `EVALSHA`). The caller needs the connection and the namespace without
   asking the owner. **The handle question is Q1.** Either way:
   - Wrap the Redix call in `try ... catch :exit, r -> {:error, {:exit, tag}}`, so a dead
     connection is `{:error, _}` and never a crash in `Session.run/2`. Today a dead owner exits the
     caller, so this improves on today.
   - `register/3`, `unregister/2`, the monitors and the refresh stay in the owner.
2. **Refresh becomes one pipeline per chunk.**
   - Keep `@pexpire_if_owner`, but run it with `EVALSHA`, falling back to `EVAL` on `NOSCRIPT`.
     Copy the existing `eval/4` helper from `memory_store/redis.ex:245-256`.
   - Send the commands with `Redix.pipeline/2` in chunks of 1,000 (the probe: 14 ms for 5,000 keys).
   - Check every result for `%Redix.Error{}`. **What to do with a `0` result is Q2.**
3. **Tests, all deterministic:**
   - **No owner hop:** `:sys.suspend(owner)`, then assert `whereis` still returns `{:ok, pid}`
     and `:none`, then `:sys.resume(owner)`. Add it to the `:redis` registry tests.
   - **Untagged connection-error test:** keep `redis_backend_error_test.exs:20` as is. It must
     still give `{:error, %Redix.ConnectionError{}}`, now from the caller.
   - **Refresh:** register 3 pids and overwrite one key with `SET` from a raw connection. Then
     `send(owner, :refresh)` followed by `:sys.get_state(owner)`; that call is the
     synchronization, no sleep. Assert:
     - `PTTL` was reset on the two keys we own.
     - The Q2 behaviour on the stolen one.
   - **Contract and distributed tests unchanged:** `redis_test.exs`, `redis_via_test.exs` and
     `redis_distributed_test.exs` pass as they are, apart from handle construction if Q1 picks the
     struct handle.
4. **Telemetry:** none required. If Q2 takes the "log and emit" option, the new event
   `[:normandy, :session_registry, :ownership_lost]` must be documented in the `Normandy.Telemetry`
   moduledoc, which `test/telemetry/catalogue_test.exs` enforces.

### PERF-8: in-flight index plus `delete_session/2`

Smallest change that meets "pruned + session delete" (the design choice is Q3; this is option B):

1. **New callback:** `@callback delete_session(handle, session_id) :: :ok | {:error, term()}`. It
   is idempotent, removes the session's turn state, template, index membership and its entries
   (fork-shared entries are Q4), and a missing session is `:ok`.
2. **The eager index holds only in-flight sessions.** `save_turn_state` gets the flag in the same
   write, so the index can never disagree with the persisted state across a crash. The flag:
   `resumable: data.resume_policy == :eager and resumable?(ts)`.
   - It is computed in `Turn.Server.persist_turn_state/2` (`turn/server.ex:1578`). That is one
     function serving all three persist sites (`:1261, 1322, 1330`).
   - No new Turn core effect is added, so `Turn.Driver` and `Turn.Inline` need no change. They
     already ignore `{:persist, _}`.

   Per backend:
   - **Redis:** a new key `"#{ns}:inflight"` (`SADD`/`SREM` pipelined with the `HSET`; the result
     list is checked for in-band errors).
   - **Postgres:** a `resumable boolean` column with a partial index
     (`WHERE resumable`), added by a new migration module. Released migrations cannot change.
   - **Mnesia:** a `resumable: true` key in the session data map. Old rows read it as `false`.
     List with `:mnesia.select` on the map pattern.
   - **ETS:** a `{{:inflight, sid}}` row.
   - **InMemory:** a `MapSet` in the Agent state.

   `list_resumable/1` returns the in-flight set. The reaper keeps its `non_terminal?` and `whereis`
   guards unchanged, as defence in depth. They now run only over in-flight ids.
3. **`save_config_template` stops maintaining the eager set.** On Redis, the `SADD`/`SREM` at
   `redis.ex:164-167` disappears, and the old `"#{ns}:resumable"` key is never read again
   (MIGRATING says it can be deleted).
4. **Public delete: Q5.** Recommended: `Turn.Session.delete/1`. It finds the live server with
   `whereis`, stops it through the supervisor, then calls `store.delete_session`.
5. **Optional, decisions.md:41:** `reap/1` checks the in-flight ids with
   `Task.async_stream(max_concurrency: 16, ordered: false)`. This is now cheap, because the list
   is short.
6. **Tests:**
   - **Contract, `session_store_contract.ex`** (it runs on all 5 backends):
     1. `list_resumable` contains a session only after an in-flight eager save, and loses it after
        a terminal save. This replaces `:99-107`.
     2. After `delete_session`, `list_resumable` shrinks, `history` is `{:ok, []}`, and both loads
        are `:error`. Calling `delete_session` twice is `:ok`. This is the plan's acceptance
        ("the eager set shrinks after a session is deleted").
     3. Deleting the parent of a fork leaves the fork's `history` intact, and the reverse.
   - **Turn.Server:** a test with InMemory and an eager session. It parks at an approval (the
     index has the id), then approves and finishes (the id is gone).
   - **Update:**
     - `session_test.exs:484` and `resume_reaper_test.exs`.
     - `redis_combo_distributed_test.exs`.
     - The 6 stub stores (if the arity changes).
     - The 34 `save_turn_state(` call sites (only if option B changes the arity).

### PERF-10: one row per document (ETS, Mnesia) with a counter row

1. **ETS:**
   - **Table:** `:ordered_set, :protected, read_concurrency: true`. Document rows are
     `{{ns, path}, %{content, version, updated_at}}`, plus one totals row per namespace,
     `{{ns, 0}, bytes, count}`. The integer `0` sorts before every binary path in term order,
     so the totals row stays inside the namespace's key range.
   - **Reads stay in the caller:**
     - `get` is a single `:ets.lookup(table, {ns, path})`.
     - `list` walks the range starting at `{ns, prefix}` (`:ets.next/2` or a bounded
       `:ets.select/3`). It stops at the first key outside the prefix, filters with
       `MemoryStore.at_or_under?/2`, and takes `list_limit/0`. Ordered-set order is byte order,
       which the contract requires (`memory_store_contract.ex:84`).
   - **Writes stay serialized through the owner:**
     - `put` reads the doc row and the totals row, runs `MemoryStore.check_limits/3` on
       `{bytes, count}`, then writes both rows.
     - `delete_tree`, `rename` and `delete_namespace` walk the range.
   - **Kept:** the handle `{pid, tid}` and the "direct read on a dead table raises" behaviour
     (`memory_test.exs:704-730`).
2. **Mnesia:**
   - **Table:** a new attribute list `[:key, :doc]`, `type: :ordered_set` (so
     `MnesiaSetup.create_table!/4` takes a type argument, and the session store keeps `:set`). The
     same `{ns, path}` and `{ns, 0}` keys as ETS.
   - **Locks:** every write first takes `:mnesia.read(table, {ns, 0}, :write)` on the totals row.
     That serializes the namespace, as today's namespace row does. `get` reads one row with a
     read lock. `list`, `rename`, `delete_tree` and `delete_namespace` use `:mnesia.select/3` on
     `{{ns, :"$1"}, :_, :_}`. A `select` locks the whole table: read for `list`, write for
     `rename`/`delete_tree`. The cost is that a rename in one namespace briefly blocks writes in
     the others. That is acceptable for rare operations; noted as a known limit.
   - **Pinned test:** update `mnesia_test.exs:35`. No data migration is needed, because
     MemoryStore is unreleased (Surprise 4).
3. **Shared code:** Docs stays for InMemory. ETS and Mnesia share a new private module,
   `MemoryStore.Rows`, with the CAS, limit, rename and tree rules over a small row-access
   interface (`fetch/2`, `put/3`, `delete/2`, `range/2`). Its two implementations, ETS and Mnesia,
   both exist now, which meets the composition rule.
4. **Tests:**
   - The contract must pass unchanged on ETS and Mnesia (`mix test
     test/behaviours/memory_store/`, untagged). It must also stay unaffected on Redis and Postgres.
   - Add a layout test per backend, with no timing:
     - **ETS:** after N puts in one namespace, `:ets.info(tid, :size) == N + 1`, and
       `:ets.lookup(tid, {ns, path})` returns the document.
     - **Mnesia:** `table_info(:attributes) == [:key, :doc]` and `table_info(:type) == :ordered_set`.
   - Record the probe numbers as the before figures. Do not add a timing assertion.

### PERF-12: the write and its `WAIT` on a non-shared connection

- **When a wait is set, the waited write and its `WAIT` run together** on a connection used for
  nothing else. Both must use the same connection (Surprise 1). The shape (a pool in the handle,
  or a store-owned connection) is Q6.
- **Pick the connection by session.** With `:erlang.phash2(session_id, k)`, a session's writes
  stay in order on one connection, and different sessions do not queue behind each other's
  `WAIT`.
- **Fix the combo too.** `Cluster.redis_child_specs/1` must stop handing its single connection to
  a store that waits.
- **Test (`:redis`, deterministic):**
  1. Build a handle with `wait: {1, 60_000}` (the test Redis has no replica, so the wait blocks).
  2. Get the waiting connection's id with `CLIENT ID`.
  3. Start `append_entry` in a Task.
  4. Poll `INFO clients` until `blocked_clients >= 1`, using `Eventually.wait_until/2`.
  5. Assert that a registry `whereis` (or a `PING`) on the shared connection returns while
     `Task.yield(task, 0) == nil`.
  6. `CLIENT UNBLOCK <id>`, then assert the task returns `{:error, {:wait_unmet, 0, 1}}`.

  The probe verified both `CLIENT UNBLOCK` and the blocked-clients signal.
- **Keep** `redis_wait_test.exs` and the `check_wait!` tests.

### B5: ETS SessionStore with one row per entry

- **Rows:** `{{:entry, sid, id}, %Entry{}}`, plus `{{:head, sid}, id}`. The turn-state and
  template rows stay as they are, and the in-flight row from PERF-8 is added.
- **append:** look up the head, then insert the entry and the head: O(1).
- **history:** walk `parent_id` with lookups from the head (O(n), done once at start).
- **fork:** check that `{:entry, sid, from}` exists, then copy the chain from `from` back to the

  including ones the new head cannot reach.
- **Unchanged:** the handle (the owner pid) and the `:private` table. Reads still go through the
  owner, so the handle shape and `store_options_test` stay as they are.
- **Test:** the contract, plus one structural test. `ets:info/2` works on a private table from
  another process, so after N appends assert `:ets.info(tid, :size) == N + 1`; get the tid with
  `:sys.get_state(pid)`. No timing assertion.

## Questions for Q

**Q1 — How the Redis registry reaches its connection without the owner (PERF-6).**
Options:
- (a) **A handle value.** `%SessionRegistry.Redis.Handle{owner:, conn:, namespace:}`, built by
  `new/1` and `Cluster.redis_child_specs/1`, with the via term `{handle, sid}`. This breaks hosts
  that pass `{SessionRegistry.Redis, MyOwnerName}`, so it needs a MIGRATING entry.
- (b) **`:persistent_term`** keyed by `{SessionRegistry.Redis, owner}`, written in `init/1`. The
  handle is unchanged and the change is non-breaking. But it is hidden global state, which your
  global rules forbid. A restarted owner rewrites the key, which triggers a global GC. Each
  `new/1` in tests leaves a key behind.
- (c) A public named ETS table per owner.

Recommendation: (a). It mirrors `SessionStore.Redis`'s `{conn, ns}` value handle and has no
hidden globals. The break is small: hosts already build `{Mod, handle}` tuples. Cost if wrong:
another public-shape change after 2.0.

**Q2 — What the refresh does when a key it owns turns out to be lost (`pexpire_if_owner` returns 0).**
Options:
- (a) Re-claim with `SET NX PX`. If another node holds the key, log it, emit
  `[:normandy, :session_registry, :ownership_lost]` and stop the local server with
  `{:shutdown, :registration_lost}`. This fences split-brain.
- (b) Re-claim only, and log.
- (c) Ignore, as today.

Recommendation: (a). A duplicate server writing the same session is the July "no single-writer
fencing" item. Cost if wrong: a stop during a brief Redis failover kills an in-flight turn, which
then resumes per its policy.

**Q3 — Is the eager index "in-flight sessions", and how does the server feed it (PERF-8)?**
This is breaking for third-party `SessionStore`s.
- **(A) A new callback.** `set_resumable(handle, sid, boolean)`, called by Turn.Server when the
  flag flips. The flag flip is a separate write, so a crash between the two writes can leave the
  index wrong.
- **(B) A new argument.** `save_turn_state(handle, sid, state, resumable?)`: one atomic write. It
  touches 34 test call sites and 6 stubs.
- **(C) Keep the "all eager" semantics** and add only `delete_session/2`. That meets the
  acceptance's letter, but `:nodedown` still scans every live eager session.

Recommendation: (B). The index can never disagree with the persisted state, and every
backend does it in one round trip. Cost if wrong: one more callback change after 2.0.

**Q4 — What `delete_session/2` does with entries a fork still uses (Postgres, Mnesia).**
Options:
- (a) **Conservative GC.** Delete only the head-side part of the chain that no other session
  reaches. An entry counts as shared if it is another session's head or has a child outside this
  chain.
  - Postgres: one transaction, using the existing `parent_id` index.
  - Mnesia: needs a full entries scan per delete, because `parent_id` sits inside the data map.
- (b) **Metadata-only delete** on those two backends: the entries stay, and this is documented as
  not erasure.
- (c) **Refuse** to delete a session that has forks: `{:error, :has_forks}`.

Recommendation: (a) for Postgres. For Mnesia, (a) with the scan, documented as O(entries). Cost if
wrong: retention and erasure promises.

**Q5 — Should there be a public `Turn.Session.delete/1`?** It would stop the live server, then
delete the stored session. It races with a concurrent `run/2`, which could restart the session;
document that. Recommendation: yes. Without it, the store callback has no caller in the library,
and the hosts that need retention would have to stop servers themselves.

**Q6 — Where the `WAIT` connection comes from (PERF-12).**
Options:
- (a) `SessionStore.Redis` owns a small pool of `k` Redix connections for waited writes, with a new
  `new/1` option `:wait_connections` (default 4). The handle carries them, and
  `Cluster.redis_child_specs/1` starts the pool when `config :normandy, :redis_wait` asks for
  replicas.
- (b) The host passes a dedicated connection. Document that it must not be shared, and have
  `redis_child_specs/1` take a second `:store_redix` keyword.
- (c) `WAIT` only once per turn boundary (on `save_turn_state`). That changes the documented
  "every write" fail-closed promise (`redis.ex:17-23`).

Recommendation: (a), with (b)'s `:store_redix` as an override. Either way, the write and the
`WAIT` must share the connection (Surprise 1). Cost if wrong: the handle tuple changes shape
again.

**Q7 — Is this a MIGRATING note, or nothing?**
- The Redis in-flight key replaces `"#{ns}:resumable"`.
- Postgres needs a new migration module.
- Sessions in flight at upgrade time are not in the new index until their next persist, so a node
  lost during the rolling deploy misses them.

Recommendation: a MIGRATING section, plus the guide's migration list
(`distributed_sessions.md:28-35`). The decision here is whether to backfill the new index from
non-terminal turn states. A Postgres backfill is impossible, because turn state is an opaque
blob. A Redis backfill would mean decoding every eager session. My recommendation is no backfill:
document it, and say to drain eager sessions before upgrading.
