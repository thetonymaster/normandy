## 0. Surprises

1. **PERF-3 is confirmed and measured.** The per-message encode count is exactly quadratic. I counted
   with `:erlang.trace_pattern({AgentMemory, :model_content, 1}, true, [:local, :call_count])` over N chat turns of
   `BaseAgent.run/3` with `Normandy.Test.ScriptedTextClient`:

   | N turns | `model_content/1` calls, NoOp compactor | with `Compactor.WindowManager` (`context_window: 1_000_000`, never compacts) |
   |---|---|---|
   | 10 | 100 | 400 |
   | 20 | 400 | 1600 |
   | 40 | 1600 | 6400 |

   That is N² without a compactor and 4N² with one: each boundary runs three extra full `history/1` passes even
   when nothing is compacted.
2. **The worst per-call quadratic term is not in Normandy. It is in Claudio.**
   `Claudio.Messages.Request.add_message/3` appends with `messages ++ [message]`
   (`deps/claudio/lib/claudio/messages/request.ex:176`). `ClaudioAdapter.add_messages/3`
   (`lib/normandy/llm/claudio_adapter.ex:495-506`) calls it once per message, so building one request costs
   O(N²). Measured cost: 28 µs at 100 messages, 1.0 ms at 600 and 4.6 ms at 1200, the same order as
   `history/1` itself. `add_tool` has the same pattern (`request.ex:662`), but tool counts are small.
   Caching encodings in Normandy alone cannot make a call linear. This needs Claudio 0.7.1 or a workaround (Q3).
3. **B3 costs almost nothing.** Measured per call: `generate_prompt` 1 µs, the output-schema pretty JSON 17 µs,
   `Toolset.to_tool_schemas` (4 tools) 3 µs, `prefix_key` phash2 2 µs, `StructuredOutputs.schema_for`
   (`SchemaTranslator.translate`) about 1 µs. That totals about 25 µs per call. History costs 5.7 ms at 1200 messages.
   The prompt also cannot be cached whole: context providers are called on every build
   (`system_prompt_generator.ex:64-77`, `ContextProvider.get_info/1`), and the output schema is appended after
   them (`base_agent.ex:1402-1412`). See Q4.
4. **Some of the per-message work is not JSON at all.** Chat input and output go as raw text
   (`agent_memory.ex:170-178`). A `ToolCallResponse` becomes a block list with no JSON
   (`tool_call_response.ex:108-170`). A `ToolResult` JSON-encodes only a non-binary, non-number output
   (`tool_result.ex:30-32`). An io_schema and a map are encoded whole (`schema.ex:424-428`,
   `base_io_schema.ex:24-27`). The token estimator re-encodes too: `estimate_block_tokens/1` JSON-encodes every
   `tool_use` and `tool_result` block map on every estimate (`context/window_manager.ex:226-228`). For an
   acceptance about "encodings" to be meaningful, the cache has to cover the wire term **and** the token
   estimate.
5. **The acceptance cannot mean "total bytes encoded is O(N)".** The Messages API is stateless, so every
   call sends the whole conversation. Claudio/Req JSON-encode the full body on every call: 6.4 ms for a
   1.6 MB body at 1200 messages. That part stays O(N) per call and O(N²) over a conversation. The acceptance
   is testable as "Normandy-side message encodings (`BaseIOSchema.to_json` of memory content, plus the JSON
   encodes inside token estimates) are O(N) over N turns". Plan-wave-6 should word it that way.
   Pre-encoded fragments (`Jason.Fragment`) on the wire would need Claudio changes plus the `Normandy.JSON`
   adapter abstraction. That is 2.x material.
6. **`drop_stale_thinking/2`'s result is thrown away on every call** (`base_agent.ex:253-256`,
   `:1432-1437`). It is recomputed from the stored memory each time. Its cost is O(N) walks and no encodes
   (0.23 ms at 1200 messages). But a cache on the entry would be invalidated per call for every stale entry
   unless the drop is applied to the cached wire term instead. `drop_thinking/1` on a block list
   (`agent_memory.ex:321`) gives the same result as re-encoding a `ToolCallResponse` with `thinking: []`
   (`tool_call_response.ex:117-126`, `replayed_blocks/2` rejects exactly the thinking blocks). So no
   re-encode is needed (proposal step 2).
7. **The compactor's rebuild is itself O(N²) when `max_messages` is set.** `rebuild_memory/2`
   (`context/window_manager.ex:411-430`) and `Summarizer.rebuild_memory_with_summary/4`
   (`context/summarizer.ex:490-513`) call `AgentMemory.add_message/4` once per kept message. Each call runs
   `Options.validate!` (NimbleOptions) and `enforce_max_messages/1`, and the latter walks the whole chain when
   `max_messages` is set (`agent_memory.ex:447-449`). With encode-at-append, the rebuild would also re-encode
   every kept message.
8. **The ETS SessionStore keeps one row per session** and re-inserts the whole `AgentMemory` on every
   `append_entry` (`behaviours/session_store/ets.ex:104-110`). That makes every append O(N). PERF-10 names only
   the MemoryStore ETS/Mnesia layout. This is the same defect in SessionStore, on the Turn.Server hot path.
   It belongs with Task 6.3, not 6.1 (Q7).
9. **AX-12 is partly fixed already.** Under the compactor, the reserve defaults to the agent's `max_tokens`
   (decision 16b; `behaviours/compactor/window_manager.ex:126-145`). Still open: the system prompt and tools
   are not counted (`context/window_manager.ex:150-158` sums history only), the estimate is chars/4 via
   `String.length/1` (`:134-138`), the standalone `Context.WindowManager.new/1` still defaults
   `reserved_tokens: 4096` (`:55`, `:68-72`), and `usage.input_tokens` is never used.
10. **AX-19 is partly fixed.** The prompt copy of the schema no longer carries `$schema`/`title`
    (`schema/wire.ex:31`). The double send itself is still there: `with_output_schema/2` always appends
    (`base_agent.ex:1400-1412`), and the adapter also sends `output_config.format`
    (`claudio_adapter.ex:247-253` converse, `:350-358` stream, selection in `:1469-1479`).
11. **AX-20 still holds as reported.** In addition, Claudio 0.7.0 already ships
    `Request.add_system_message/3` (`deps/claudio/lib/claudio/messages/request.ex:1561`), so the agentx
    "mid-conversation system message" variant needs no Claudio work.
12. **Turn.Server compaction persistence (deferred to "Wave 6" by decision 22) has no task in plan.md.**
    It is still present (`hooks/handlers.ex:66-68` comment; the `:compact_result` handler only swaps `config`,
    `server.ex:779-788`). It touches the compactor and the store format, not encoding. See Q6.

## 3. AX-12 — context budgeting undercounts the real prompt

Current: `Context.WindowManager.estimate_conversation_tokens/1` sums memory only (`context/window_manager.ex:150-158`),
using chars/4 via `String.length` (`:134-138`). The compactor's budget is `context_window − reserved`, with
`reserved` defaulting to the agent's `max_tokens` (`behaviours/compactor/window_manager.ex:126-145`; fixed by decision
16b). The standalone default is still 4096 (`context/window_manager.ex:55`, `:68-72`). The compactor `ctx` is
`%{model, window, mid_round}` (`behaviours/compactor.ex:55`, built at `base_agent.ex:912`). It carries no
system/tool size and no previous `usage`. Usage is never kept on `Turn.State` (only `tokens_compacted`).

**Verdict: stay deferred to 2.x.** Reasons:
1. Task 6.1 should be a pure refactor whose proof is "the same wire bodies and the same estimates". Changing
   the estimator in the same task removes the before/after equality check (`compactor_test.exs:370-410`
   compares against the old formula).
2. The usage-based trigger needs a new persisted `Turn.State` field (the last call's
   `input_tokens + cache_*`) and a `ctx` key. That is persisted-format and behaviour-contract work.
3. 6.1 makes the later fix cheap: once each entry's token estimate is cached, adding `system + tools` is one
   integer more per boundary.

If Q wants a piece now, the smallest safe one is a new `ctx` key `:prompt_tokens` (an estimate of system prompt
plus tool JSON) that `Compactor.WindowManager` adds to `tokens_before`/`tokens_after`. The key is additive for
implementers, and `tokens_removed` is unchanged. Do it as a separate sub-task after 6.1 (Q5).

## 4. AX-19 — output schema sent twice under structured outputs

Current: the system prompt always gets `# OUTPUT SCHEMA` (`base_agent.ex:1400-1412`; the shown schema is
chosen by `prompt_output_schema/2`, `:1384-1386`). The adapter sends `output_config.format` when `__structured_schema_for__/2` returns `{:ok, _}`
(`claudio_adapter.ex:1469-1479`, `:247-253`, `:350-358`). After a 400 that names the format, it falls back
without the format, and that request still relies on the schema text being in the prompt.

**Verdict: stay deferred to 2.x.** Reasons:
1. Only the adapter knows whether the structured path applies. That depends on the client type,
   `:structured_outputs` and translatability, and it changes mid-call on the 400 fallback. BaseAgent builds
   the prompt before that decision, so removing the schema needs the adapter to add the text on fallback.
2. The system prompt is part of `prefix_key`. A fallback that changes the system prompt stamps a response
   with a key for a prompt it was not produced under, so replayed thinking could 400. Getting that right
   is replay work, not performance.
3. It changes model-facing text, which only a live run can validate (Task 7.6 runs once). The gain is tokens,
   not CPU, and it is smaller with caching on.

## 5. AX-20 — volatile context in the single cached system block; caching off by default

Current: providers are rendered into the one system string (`system_prompt_generator.ex:45-47`, `:64-77`) and the
schema is appended after them (`base_agent.ex:1402-1412`). `enable_caching` defaults to false
(`claudio_adapter.ex:43`, `:779`). With it on, the whole system string gets one breakpoint
(`claudio_adapter.ex:526-533`), plus the automatic conversation breakpoint (`:495-501`) and the last tool's
(`:805-830`). `Request.system` is typed `String.t() | nil` (`llm/request.ex:41`). A provider change also
changes `prefix_key`, so all replayed thinking is dropped.

**Verdict: stay deferred to 2.x, except that Q decides now on the default (Q5).** Reasons:
1. Splitting the system prompt into stable and volatile blocks changes `Request.system`'s type, which every
   `Model` implementation sees (the protocol is public; 2.0 is unreleased, so this is cheaper now than later,
   but it is a protocol change, not a 6.1 refactor). It also changes `OpenAICompatibleAdapter`.
2. Moving the schema before the providers changes the prompt text, which needs live validation.
3. Making `enable_caching: true` the default is a default and cost change. A cache write costs 1.25× input,
   so a one-call agent pays more. It belongs in the MIGRATING list and needs Q.

## Proposed approach

Design principle: **6.1 changes no wire byte and no estimate.** The proof is (a) the counting test and
(b) `WireScript` bodies identical to today's for the same scripted conversation.

### Step 1 — cache each entry's model-facing term and token estimate (PERF-3)
- `Normandy.Components.AgentMemory.Entry` gains two derived fields, `wire: nil` (what `model_content/1` returns:
  a string or a block list) and `tokens: nil` (`WindowManager.estimate_message_content_tokens(wire) + 10`). They
  are documented as derived and never persisted. Alternatively, a private side map on `%AgentMemory{}`
  (Q1).
- One private `AgentMemory.put_content(entry, content)` sets content, `wire` and `tokens` together. It is used by
  `add_message/4` (`:81-87`), `drop_stale_thinking/2` (`:280`), `delete_turn/2` (`:245`),
  `enforce_max_messages/1` (`:463`), `from_entries/1` and `load/1`. `model_content/1` moves to
  `Entry`/AgentMemory as the single encoder.
- `history/1` reads `Map.get(entry, :wire) || model_content(entry.content)`. `Map.get` is needed for entries
  decoded from a pre-field template. The fallback keeps hand-built memories working, and its output is unchanged.
- The token estimate moves to `AgentMemory` (or `Context.TokenEstimate`). `Context.WindowManager` calls
  `estimate_message_content_tokens/1`, and `AgentMemory` must not depend on `Context`. Simplest: AgentMemory calls
  `Normandy.Context.WindowManager.estimate_message_content_tokens/1` (one-way dependency, no cycle today).
- `WindowManager.estimate_conversation_tokens/1` sums `entry.tokens` over `entry_chain/1`, using the same fallback.

### Step 2 — one walk per request, stale thinking applied to the cached term
- New `@doc false AgentMemory.request_messages_for(memory, prefix_key) :: [Message.t()]`. It runs
  `thinking_verdict/3` on the stored content, then on `:drop` emits `drop_thinking(entry.wire)` (a list filter,
  Surprise 6) instead of re-encoding. Then it merges the tool runs exactly as `request_messages/1` does.
  `drop_stale_thinking/2`, `history/1` and `request_messages/1` stay public and unchanged for their tests.
- Call sites: `base_agent.ex:253-261`, `:1432-1437`, `token_counter.ex:183-193`.
- Equivalence property test (StreamData is already a dep: `test/agents/turn_property_test.exs`): for random
  `ToolCallResponse`s (with/without `content_blocks`, thinking, non-map tool input),
  `drop_thinking(to_json(r)) == to_json(drop_thinking(r))`.

### Step 3 — the compactor stops re-encoding (amplifier)
- `Behaviours.Compactor.WindowManager.run/2` (`:150-173`): compute `before` once. If it is within the budget, return
  `%{compacted: false, tokens_before: before, tokens_after: before, tokens_removed: 0, strategy:, dropped: []}`
  without calling `ensure_within_limit/2`, the after-estimate or `dropped_entries/2`. **Check:** today's
  no-op meta has the same keys with `tokens_after == before` and `dropped == []`, so `after_compact` does not run
  (`hooks/handlers.ex:70`). Confirm against `compactor_test.exs` before changing.
- `tokens_removed_this_turn/2` (`:187-194`) sums `entry.tokens` instead of calling `to_json`.
- New `@doc false AgentMemory.keep_entries(memory, kept_entries, opts)`. It rebuilds from kept `%Entry{}`s in
  one pass, re-linking `parent_id` and dropping thinking via `put_content/2`. A cached JSON string stays valid
  because thinking lives only in `ToolCallResponse`/block lists. It skips per-message `Options.validate!` and
  `enforce_max_messages/1`. Used by `context/window_manager.ex:411-430` and `summarizer.ex:503-513`. Fixes
  Surprise 7.
- `truncate_oldest_first/2` and `estimate_messages_for_tokens/2` read cached tokens instead of `history/1`.

### Step 4 — Claudio's `++` (Q3; recommended: a Claudio 0.7.1 bulk `add_messages/2`)
- Claudio side: `Request.add_messages(request, [{role, content}])` builds the list once (one `++` per call) and
  keeps `normalize_content/1` and the fallback-beta check. Normandy's `add_messages/3` (`claudio_adapter.ex:495-506`)
  maps each `%Message{}` to `{role_atom, wire_content}` through the existing `add_single_message` branches,
  then calls it once.
- Without a Claudio release, the workaround is for Normandy to build each message with `add_message/3` on an
  empty `Request.new/1`, take `.messages` and `.betas`, and set `%{req | messages: list}` once. That couples
  Normandy to Claudio's struct fields, so I don't recommend it.

### Step 5 — B3 (Q4; recommended: close by measurement plus one cheap change)
- Record the 25 µs measurement and do not cache the prompt: providers make it impure.
- Optional: `Toolset.register/3` precomputes the wire schema (`%{name, description, input_schema}`) into a new
  `Toolset` field, and `to_tool_schemas/1` returns those values. The toolset is not persisted
  (`config_template.ex:229`), so there is no format risk.
- Optional: memoize the `# OUTPUT SCHEMA` text per schema module in `:persistent_term`
  (`{Normandy.Agents.BaseAgent, :output_schema_text, module}`). It is written once per module, so the global GC
  cost on write is paid once. Only worth it if Q wants B3 closed with code.

### Acceptance test (no new telemetry event)
File: `test/agents/linear_history_test.exs` (async).
1. A test struct `CountingContent{ref}` with `defimpl Normandy.Components.BaseIOSchema` whose `to_json/1` does
   `:counters.add(ref, 1, 1)` and returns `"counted"`. Seed the memory with K counting entries
   (`AgentMemory.add_message/3` on `config.memory`), then run N turns of `BaseAgent.run/3` with
   `ScriptedTextClient`. Assert the counter equals K (each entry encoded once, at append) for N = 1 and N = 20.
   Repeat with `Compactor.WindowManager, context_window: 1_000_000` (never compacts), then with a window that
   compacts once (after a compaction the count may grow only by the number of entries the summary/rebuild adds).
2. A tool path: a tool returns `%CountingOutput{ref}` with a test `Jason.Encoder` impl that counts. Dispatch encodes
   it twice per result (`dispatch.ex:288-299` `ensure_encodable/1`, `:457` cap), and the cached wire encodes it
   once. Assert `count == 3 * results` after N turns. A count that is independent of N means O(N) in total.
3. The same two assertions through `stream/3` (`ScriptedTextClient.stream/3`) and through `Turn.Session` with
   the InMemory store (rehydration encodes each entry once, via `from_entries/1`).
4. A `WireScript` test: the same scripted 3-turn conversation with a tool round and thinking, on before/after
   builds. Freeze the decoded bodies from today's code into a fixture first, so the test fails if any byte
   changes.
No sleeps, no timing. The counts are deterministic, and the "O(N)" is the count staying constant per message as N grows.
If Q prefers a global count over `Normandy.JSON.encode!/2`, `:erlang.trace_pattern(..., [:call_count])` works
(I used it for the baseline) but needs `async: false`.

Telemetry: no new or changed event, so the catalogue test is unaffected.

### Behaviour changes to call out (MIGRATING / Q)
- An unencodable io_schema in memory (for example a tuple inside an `:any` field) raises at **append** instead of at
  the next LLM call. Under Turn.Server that is `{:handler_crashed, :append, e}`, failing the append before the
  store write (`server.ex:1244-1258`), instead of the LLM worker's error path (Q2).
- An agent's memory holds an extra string per JSON-encoded message, roughly +50–100% heap for histories heavy in
  tool results. Turn.Server copies `data` into a worker per blocking effect (`server.ex:1394`; B2, Task 6.2), and
  copying between processes does not preserve sharing.

## Questions for Q

**Q1. Where the cache lives.**
(a) Fields `wire`/`tokens` on the public `%Entry{}`. Trims, deletes and forks maintain them automatically. They are visible in
`after_compact`'s `dropped` and in `initial_memory` templates.
(b) A private map `%AgentMemory{encoded: %{id => {wire, tokens}}}`. `Entry` stays as the store contract sees it, but
every mutation path must maintain the map.
*Recommend (a)*, with `ConfigTemplate` stripping the fields when the template is built and `rebuild/3` refilling them.
*Cost if wrong:* (a) adds a public struct field that hook authors may pattern-match on. (b) risks a stale map entry
after a missed mutation path, which would send the wrong content to the model.

**Q2. Encoding failures move from the LLM call to append.**
(a) Accept it and add a MIGRATING line.
(b) Rescue at append, leave the cache `nil`, and let the call-time fallback raise where it does today.
*Recommend (a)*: the error surfaces closer to its cause, and (b) is a silent fallback in all but name.
*Cost if wrong:* a Turn.Server user whose alerting matches `:task_down` for this case sees `:handler_crashed`
instead. The case is rare: Dispatch already turns unencodable tool output into an error result.

**Q3. Claudio's O(N²) `add_message` (Surprise 2).**
(a) Claudio 0.7.1 gains `Request.add_messages/2`, and Normandy bumps to it (6.1e). It can ride the 0.7.1 release
already pending for citations replay.
(b) A Normandy-side workaround that writes `request.messages` directly.
(c) Leave it.
*Recommend (a).* *Cost if wrong:* with (c), a 1200-message call still spends about 4.5 ms (quadratic) building
the request after 6.1, which is most of the remaining Normandy-side cost.

**Q4. B3 scope.** Measured at about 25 µs per call.
(a) Close B3 with the measurement and no code.
(b) Also precompute tool schemas in `Toolset` (6.1f).
(c) Also memoize the output-schema text per module.
*Recommend (a)* or (b). A full prompt cache is impossible without first splitting the providers out (AX-20).
*Cost if wrong:* under 0.1 ms per call.

**Q5. AX-12 / AX-19 / AX-20.** Confirm all three stay deferred to 2.x (reasons in §3–5). Two items need your
decision even if deferred:
(i) Should the AX-12 `ctx.prompt_tokens` piece go in now as a separate sub-task after 6.1? I recommend no.
(ii) Should `enable_caching` default to `true` in 2.0? It is a default and cost change, cheaper to make before
release than after, and it needs a MIGRATING entry. I recommend yes for 2.0, because tool loops re-pay the full
prefix every iteration without it, but this is your pricing call.

**Q6. Turn.Server compaction persistence** (decision 22 deferred it to "Wave 6", and no 6.x task names it).
(a) Add it to 6.2 (Turn.Server store IO), as a compaction-marker entry across the 5 SessionStore backends
(a persisted-format change).
(b) Its own task 6.1g after 6.1c.
(c) Keep it as a documented known limit (MIGRATING §… already says so; `MIGRATING-2.0.md:1148`).
*Recommend (a)*: it is store-format work like the rest of 6.2. *Cost if wrong:* a rehydrated session replays the
uncompacted history, which means a cache miss and a re-summary, and rarely a 400 on replayed thinking.

**Q7. SessionStore ETS: one row per session, O(N) per append** (`ets.ex:104-110`, Surprise 8). Fold it into
6.3 next to PERF-10's MemoryStore row layout? *Recommend yes.* It is not 6.1's acceptance.
