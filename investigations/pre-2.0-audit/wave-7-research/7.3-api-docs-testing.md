### 2.2 What a user needs (and what the protocol requires)

From `Normandy.Agents.Model` moduledoc (model.ex:16-65) and `Normandy.LLM.Request` (request.ex):
a client fills `request.response_model` — `nil` → text; `%BaseAgentOutputSchema{}` → `chat_message`;
`%ToolCallResponse{}` (any agent with tools or MCP servers, base_agent.ex:602-608) → `content` /
`tool_calls` / `stop_reason`; a custom output schema → the filled struct. `stream/3` returns
Anthropic-shaped SSE event maps (atom `:type` etc., string-keyed nested maps). Every shared client
carries `options: %{}`; it is **not** required by `BaseAgent.run/3` for a non-Claudio client
(probe `noopts.exs`: a client struct with no `:options` field runs) — `client.options` is read
only in ClaudioAdapter paths (structured_outputs.ex:13 is called from claudio_adapter.ex:1478,1483)
and via `Map.get` in telemetry/provider.ex:52.

A user writing a test today must: implement the protocol (both functions), know the
response_model-filling convention, hand-write SSE maps to test streaming, and either put the impl in
`test/support` (compiled before consolidation) or set `consolidate_protocols: false` — a `defimpl`
inside a `.exs` test file is not dispatched under a consolidated protocol (the note DX-8 cites lives
only in Normandy's own mix.exs:14). A lib-shipped client is consolidated in the user's build, so
none of that applies. Also MIGRATING-2.0.md:1699-1703: Mox/Req.Test allowances must name the
worker or Turn.Server pid; a FakeClient that captures its owner pid at `new/1` sidesteps allowances.

### 2.3 Proposed public module (smallest that covers the above)

`lib/normandy/test/fake_client.ex`, `Normandy.Test.FakeClient` (name per plan.md; see Q2):

```elixir
@type reply ::
        String.t()                                    # text answer
        | map()                                       # structured answer, JSON-encoded then parsed into the output schema
        | {:tool_calls, [%{name: String.t(), input: map()}]}   # ids "toolu_fake_<n>_<i>"
        | {:stop, Normandy.LLM.Response.stop_reason(), reply()} # e.g. {:stop, :max_tokens, "par"}
        | {:error, Normandy.LLMError.t() | atom()}     # atom = LLMError type; retryable? for :rate_limit, :overloaded, :server, :transport
        | (Normandy.LLM.Request.t() -> reply())       # dynamic
@spec new([reply()], keyword()) :: t()   # opts: :notify (pid | nil, default self()), :usage (map, default %{"input_tokens" => 1, "output_tokens" => 1}), :options (map, default %{})
@spec remaining(t()) :: non_neg_integer() # scripted replies not yet consumed
```

- State: replies as a tuple + one `:atomics` counter in the struct (the WireScript pattern,
  test/support/wire_script.ex:24-36), so any process (BaseAgent task, AgentProcess worker,
  Turn.Server task) consumes the next reply. Single-node only (atomics refs do not cross nodes;
  the client is never persisted: config_template.ex:7 excludes it).
- Capture: every request sends `{Normandy.Test.FakeClient, id, %Normandy.LLM.Request{}}` to
  `:notify` (`id` = a ref kept in the struct, so two fakes in one test are distinguishable);
  `assert_receive {FakeClient, ^id, %Request{max_tokens: 16_000}}`.
- Converse: maps the reply onto `request.response_model` as in §2.2; a map onto a custom schema
  goes through `Normandy.LLM.JsonDeserializer.parse_and_validate/3` (json_deserializer.ex:160) so
  casting matches the adapter; BaseAgent validates the output again (base_agent.ex:906-922).
  `stop_reason` defaults to `:tool_use`/`:end_turn`.
- Stream: the same reply rendered as events (`message_start`, text or tool_use blocks with
  `text_delta`/`input_json_delta`, `message_delta` with stop_reason and usage, `message_stop`).
- Past the script: raises `ArgumentError` "FakeClient: request N has no scripted reply (M scripted)"
  (a bug raises; `run/3` re-raises it; under Turn.Server it becomes a `:handler_crashed` TurnError).
- No telemetry events added or changed. JSON via `Normandy.JSON` (not `Jason` directly).

### 3.2 Moving them to lib

- Compile: no guard needed (Surprise 5). The modules only `defmacro __using__`; `test`/`assert`/
  `setup` expand in the user's test module, which has `use ExUnit.Case`. Optional hardening:
  raise a clear `ArgumentError` in `__using__` if `ExUnit.Case` is not already used
  (`Module.get_attribute(__CALLER__.module, :ex_unit_tests)`-style check) — not required.
- Names: `Normandy.Test.SessionStoreContract`, `Normandy.Test.MemoryStoreContract`
  (+ `Normandy.Test.SessionRegistryContract` if Q agrees; it then inlines its 10-line poll).
- API for third parties: add `:new` (`{module, fun, args}`, default `{impl, :new, []}`) so a store
  whose handle needs config can be tested; make `:stored_entry_ids` optional (when absent, the two
  delete tests check only through the public API: history empty, `load_*` `:error`) — Q4.
- Moduledoc must state: fresh/empty handle per test; `async: false` for node-global backends; the
  contract runs real concurrency (Tasks, 5-15 s awaits).
- How others ship such suites: Ecto ships `integration_test/cases` + `integration_test/support` in
  its Hex package outside `lib` (deps/ecto/mix.exs:50-52) and adapters `Code.require_file` them —
