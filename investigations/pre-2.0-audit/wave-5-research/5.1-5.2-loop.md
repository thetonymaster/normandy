## 0. Surprises

1. **Most of AX-1's fallback half is already done (Wave 2, `0df3b46`, `9b66fac`).** `convert_turn_output`
   no longer returns `raw`. It goes through `convert_final_output/4` → `convert_final_text/3`
   (`base_agent.ex:757-820`): a chat schema gets the unwrapped text, a schema with a JSON Schema is parsed by
   `ParseFailure.parse_text_output/3`, and anything else raises `LLMError :invalid_output`. The tool loop
   already puts a non-chat OUTPUT SCHEMA in the system prompt (`prompt_output_schema/2`, `base_agent.ex:1324-1326`).
   `IO.warn` is gone: validation failure is `Schema.ValidationError` (`base_agent.ex:822-833`). Tests already pin
   this: `test/agents/base_agent_output_validation_test.exs:144-188` (struct returned, schema in prompt,
   `:invalid_output`, Turn.Server reply, ValidationError). **What is still missing from 5.1 is only the native
   `output_config.format` on tool-loop calls**, plus the CLAUDE.md and adapter-moduledoc text.
2. **The acceptance "an unparseable final answer gives `{:error, %ValidationError{}}`" contradicts the code and an
   existing test.** Unparseable text gives `{:error, %LLMError{type: :invalid_output}}`
   (`parse_failure.ex:73-81`). Pinned by `base_agent_output_validation_test.exs:160-177`, which covers both run/2
   and Turn.Server. Text that parses but breaks the schema gives `ValidationError` (`:179-185`). Review Focus #2
   says "parsed struct or ValidationError". This needs a ruling (Q1).
3. **`%Normandy.LLM.Request{}` has no `output_format` and no `tool_choice` field** (`request.ex:20-29`). Plan.md
   Task 2.1 listed both as produced interfaces, and they were never added. 5.1's acceptance ("the captured
   request carries `output_format`") and 5.2's "tools are withheld from the final call" both need new fields.
   Today a Model implementation cannot see the output schema at all during a tool loop: `response_model` is
   `%ToolCallResponse{}`.
4. **The adapter decision is a hard `:skip` for any tool-bearing call.** `__structured_schema_for__/3`
   (`claudio_adapter.ex:1398-1406`) is pinned by `test/llm/claudio_adapter_test.exs:207-214`. Claudio itself is
   fine: `set_output_format/2` merges into `output_config`, and tools plus format in one request is tested in
   `test/llm/claudio_request_capabilities_test.exs:9-25`, whose test name already says "(Task 5.1)".
5. **`stop_reason` is dropped on the sync path before anything can act on it.** `call_llm_with_resilience/3`
   destructures only `content, usage, meta` (`base_agent.ex:307-309`). Only the string `meta.finish_reason`
   survives, into telemetry, and it is not usable for control flow: OpenAI meta keeps the raw provider string
   (`"length"`, `openai_compatible_adapter.ex:138-154`), not the mapped atom. Streaming keeps it as a **string**
   (`final_message.stop_reason = "max_tokens"`, `stream_processor.ex:140,202-203`). Claudio gives an atom.
6. **`Turn.State.stop_reason` already exists with a different meaning** (`:completed | :max_iterations`,
   `turn.ex:54,135,142`). Pinned by `turn_test.exs:289` and `turn_inline_test.exs:126`. The response's stop
   reason needs another name in the core (e.g. read `Map.get(resp, :stop_reason)` and never store it, or a field
   called `finish_reason`).
7. **`LLMError` has no `:max_tokens` or `:refusal` type** (`error.ex:32-46,50-63`). `LLMError.new/1` raises on an
   unknown type, so the types must be added. Decision 20's breaker filter (`base_agent.ex:359-377`) already
   excludes them if `retryable?: false`.
8. **AX-10 is still live and pinned by tests.** On the structured path, `max_tokens`/`refusal`/context-exceeded go
   to `apply_parse_failure`, and under `:fallback` the raw truncated JSON becomes `chat_message`
   (`claudio_adapter.ex:1409-1429`). Pinned by `test/llm/claudio_adapter_test.exs:233-244` ("refusal routes to the
   parse-failure policy", "max_tokens routes to the parse-failure policy") and `:246-275`. On the legacy path, a
   truncated answer runs the **JSON retry loop** (`populate_standard_schema`, `claudio_adapter.ex:827-853`).
   `__response__/3` then stamps the **first** response's stop_reason on the result (`claudio_adapter.ex:943-950`,
   called at `:218` with `response`), even when the content came from a retry.
9. **The forced-final call changes the system prompt only for the chat schema.** Verified by the probe above:
   with a non-chat schema the system prompt is byte-identical across the loop and the final call, because the tool
   loop already shows that schema. With the chat schema it gains `# OUTPUT SCHEMA`. Tools are sent in both cases.
   `test/llm/claudio_adapter_thinking_test.exs:144-166` **pins the current behaviour**:
   `refute first["system"] == forced["system"]`, and the forced call's assistant message holds only `tool_use`,
   because `drop_stale_thinking` removed the in-flight thinking. It must be inverted. On Opus 5.5 with preserved
   thinking, dropping thinking from the middle of the history is the "history edit" the API may 400 on for
   enforced accounts (UNVERIFIED live; Task 7.6).
10. **The forced-final call skips conversion in the core** (`turn.ex:129-137`: straight to `:validate_output`). The
    streaming shell compensates with a special `final: true` clause that converts inside `call_llm`
    (`base_agent.ex:1073-1081`). If 5.2 makes the final call use the loop's response model, the core must convert
    on that path, and the streaming special case must go, or the output is converted twice.
11. **`pause_turn` cannot work until 5.3 lands.** A paused turn's content is mostly `server_tool_use`/`mcp_tool_use`
    and result blocks. `%ToolCallResponse{}` keeps only text, `tool_calls` and thinking (`tool_call_response.ex:30-35,85-121`),
    so the continuation would replay without them. If nothing else is left, the assistant message is
    `thinking ++ []`, and the adapter raises on empty content (`ensure_non_empty_content!`,
    `claudio_adapter.ex:581-587`). AX-3 makes this worse: `mcp_tool_use` is still extracted as a local tool call
    (`claudio_adapter.ex:972-1005`), so a paused MCP-connector turn currently **dispatches locally**. Plan order
    5.2 → 5.3 should be swapped for the `pause_turn` part (Q4).
12. **The API wants the cap notice persisted, not request-only.** Per `shared/prompt-caching.md` (per-turn
    reminders) and preserved thinking: a reminder added to one request and missing from the next is a history
    edit (cache miss, and on Opus 5.5/Fable 5.1 later thinking blocks are invalidated). The append-only form is
    "a text block after the `tool_result` blocks in the same user message, kept". That depends on 5.3's
    one-user-message-per-batch (AX-6). Today each tool result is its own `"tool"` message (`turn.ex:389`).
13. **`tool_choice: none` is the right "withhold" (verified):** a `tool_choice` change keeps the tools and system
    caches and invalidates only the messages cache. Removing the tool definitions would invalidate everything.
    `none` is allowed on Opus 5.5/Fable 5.1/Sonnet 5.5, unlike `any`/`tool`, and works with thinking. Claudio has
    `Request.set_tool_choice(:none)` (`deps/claudio/lib/claudio/messages/request.ex:758-760`). Changing
    `tool_choice`/`output_config` is explicitly not a thinking-invalidating edit (`model-migration.md` preserved
    thinking, "What keeps later blocks valid").
14. **ScriptedToolClient cannot express the 5.1 acceptance as is.** It returns the bare `request.response_model`
    after the tool round (`test/support/scripted_tool_client.ex:12-19`): no JSON text, no stop_reason, no request
    capture. Its only users are `test/agents/tool_context_test.exs` and `test/hooks/tool_hooks_test.exs`.
    Extending it with defaulted fields is safe.

## 2. Proposed approach

### 5.1 Output schema with tools (AX-1, decision 11)

1. **`Request.output_format`** (new field, default `nil`): the output-schema struct the final answer text must
   match, separate from `response_model`. Docs: "adapters that support constrained decoding send it, others
   ignore it". Set in `get_response_with_usage/3` when `response_model` is `%ToolCallResponse{}` and
   `config.output_schema` is **not** a chat schema (Q2). Name per plan.md; type choice in Q3.
2. **ClaudioAdapter routing**: `__structured_schema_for__/3` becomes `__structured_schema_for__(client, request)`:
   no tools → `schema_for(client, response_model)` (unchanged); tools and `output_format` set →
   `schema_for(client, output_format)`; tools and no `output_format` → `:skip`. Kill switch and incompatible
   schema still `:skip` through `StructuredOutputs.schema_for/2`.
3. **Structured handler with `%ToolCallResponse{}`**: in `converse_structured/4`, for a ToolCallResponse response
   model, check stop_reason first (5.2), then `populate_tool_call_response` (text, `tool_calls`, thinking) for
   both `:tool_use` and `:end_turn`. The `:end_turn` text is the constrained JSON and goes to `content`. That
   passes `stop_reason: :tool_use` through to the loop (decision 11) with no decode or bind in the adapter. The
   existing `convert_turn_output` parses it into the schema, so one conversion serves the structured and fallback
   paths. The 400 schema-rejection fallback stays (`converse_legacy`, same request, no format), and the system
   prompt already carries the OUTPUT SCHEMA for it.
4. **System prompt**: unchanged. The non-chat schema stays in the prompt on structured calls too (AX-19,
   double-send, MEDIUM, not in Wave 5). Changing it per call would also change the prefix key and the cache
   between the structured and fallback requests.
5. **Docs**: `claudio_adapter.ex:101-119`, `CLAUDE.md:215` (replace "tool-bearing calls" with "a tool loop sends
   the output schema as `output_config.format` alongside the tools"), `model.ex` "Response content" (new
   field), `stream/3` doc if Q5 = yes.
6. **Tests**: extend `ScriptedToolClient` with defaulted `final_text: nil` (JSON returned as
   `%ToolCallResponse{content: final_text}` after the tool round) and `notify: nil` (`{:converse, request}`):
   (a) non-chat schema comes back as the struct and the second request has `output_format: %Decision{}`;
   (b) `options: %{structured_outputs: false}` → the system prompt contains `# OUTPUT SCHEMA` and the result is the
   struct (at the BaseAgent level the kill switch is invisible to a fake client, so also add a wire test:
   Req.Test with tools and `structured_outputs: false` → `refute body["output_config"]["format"]`; with it on →
   `body["output_config"]["format"]["type"] == "json_schema"` and `body["tools"] != []`);
   (c) unparseable final text → the error per Q1. Update `claudio_adapter_test.exs:207-214`.

### 5.2 stop_reason handling (AX-4, AX-10, AX-5)

1. **New `LLMError` types** `:max_tokens` and `:refusal`, `retryable?: false` (not retried, not counted by the

## 3. Questions for Q

**Q1. Unparseable final answer: `ValidationError` or `LLMError :invalid_output`?** Plan, Review Focus #2: ValidationError. Code and tests: `:invalid_output` (decode failure) vs ValidationError (decoded but invalid).
(a) Keep the split and fix the plan text. (b) Make all of it `ValidationError`.
Recommend **(a)**: it matches the no-tools path, where the adapter's `ParseFailure` already returns `:invalid_output`, and the `:on_parse_failure` policy. Cost if wrong: (b) later is a breaking change to one error type in one path.

**Q2. Send `output_config.format` on tool-loop calls for the default chat schema too?**
(a) Non-chat schemas only. (b) Always.
Recommend **(a)**: a chat agent would otherwise answer `{"chat_message": ...}` JSON, which is then stored and replayed (AX-21). Cost if wrong: chat agents miss a guarantee they never needed.

**Q3. `Request.output_format` type.**
(a) The output-schema struct; the adapter translates via `StructuredOutputs.schema_for/2`. (b) A ready JSON Schema map; BaseAgent translates.
Recommend **(a)**: the kill switch and translator are per-client, and adapters own wire format. Cost if wrong: an internal refactor before 2.0 ships.

**Q4. Ship `pause_turn` in 5.2, or move it after 5.3?** It cannot replay server/MCP blocks before 5.3, and AX-3 dispatches `mcp_tool_use` locally today.
Recommend **moving the `pause_turn` item and its test to 5.3** (or doing 5.3 before 5.2). `max_tokens`, `refusal` and the cap stay in 5.2. Cost if wrong: a 5.2 test that passes with fakes while the live path still breaks.

**Q5. Streaming and `output_format` (AX-24).** `stream/3` with a non-chat schema could send the format too, with a one-line change in `build_stream_request/1`.
Recommend **yes**, in 5.1: same fields, same adapter builder. Cost: one more test.

**Q6. `:model_context_window_exceeded`** (today treated like `max_tokens` on the structured path).
(a) Same `:max_tokens` error, detail naming the reason. (b) Its own `:context_window_exceeded` type.

**Q7. Should an agent with `mcp_servers` but no local tools run the tool-loop response model?** Today it doesn't, so MCP-connector `pause_turn` and `mcp_tool_use` never reach the loop.
