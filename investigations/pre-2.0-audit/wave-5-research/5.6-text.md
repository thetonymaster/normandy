## 0. Surprises

1. **AX-17's mechanism is wrong, the symptom is worse.** The audit says small maps iterate "in sorted key order". Probed today:
   - Atom-keyed spec (`__schema__(:specification).properties`, what tool `input_schema` and the legacy `# OUTPUT SCHEMA` encode): order is the VM's atom-table order, not alphabetical and not declaration order. With fresh atoms `[:reasoning, :answer, :zebra_q, :apple_q, :mango_q]` it came out in declaration order (by accident of atom creation); with pre-existing atoms declared `value, type, name, id, error` it came out `error, id, name, type, value`. So the order depends on which atoms the VM already knew: non-deterministic across projects.
   - String-keyed path (`SchemaTranslator`, i.e. the structured-outputs `output_config.format` schema, `schema_translator.ex:28-31`): deterministically **alphabetical** (probe: `answer, apple_q, mango_q, reasoning, zebra_q`). This is the path constrained decoding uses, so "reasoning before answer" is impossible there today.
   - `Module.__schema__(:fields)` (`schema.ex:548`) already holds declaration order (virtual fields included).
2. **AX-11 emits `""`, not `null`** (plan.md already says so). Cause: `schema.ex:997` `Keyword.get(opts, :description, "")` then `schema.ex:589-591` `Map.put(json_type(type), :description, description)` unconditionally. The structured path is already clean (`SchemaTranslator.with_description/2`, `schema_translator.ex:58-62`, drops `""`). The empty description still reaches the model through tool `input_schema` (`tool.ex:85`, `toolset.ex:251`), the legacy `# OUTPUT SCHEMA` block (`base_agent.ex:1339`) and `RetryFeedback` (`retry_feedback.ex:28, 58`). It also reaches `Introspection.get_field_metadata/2` (`introspection.ex:245`: returns `""` today, would become `nil`).
3. **Policy default-deny shows `"error": null`.** `denial_result/3` uses `Map.get(info, :reason, "denied by policy")` (`dispatch.ex:475`), but `PolicyEngine.Ruleset` returns `%{reason: nil, rule_id: nil, rationale: nil}` for a default-action deny (`policy_engine.ex:127`, pinned by `policy_engine_test.exs:63`), so the key exists and the default never applies. Probe output: `{"error":null,"rule_id":null,"rationale":null,"denied":true,"pending_approval":false}`. Worse than AX-13 reported.
4. **Null keys are all over denials.** Probe of the sync needs_approval collapse: `{"error":"denied by policy","rule_id":null,"rationale":"r","denied":true,"pending_approval":true}`.
5. **Several AX items are already closed or moved:**

## 5. Schema declaration order: how it is built and what preserves it

Current path:
1. `field/3` stores `{name, {type, description, opts}}` in `:schema_fields` in declaration order (`schema.ex:1026-1027`).
2. `__schema__/1` builds `properties` from a list comprehension (ordered) and calls `Map.new(properties)` (`schema.ex:536-546`): order is lost here. The map is `Macro.escape`d into the module (`:555`) as a literal.
3. Consumers read `spec[:properties]` as a map with `Map.get/Access/pattern match` in 7 lib modules: `schema/validator.ex:245,268`, `schema/introspection.ex:115-116,236-237,297,331`, `tools/input.ex:128,151`, `llm/json/schema_translator.ex:23`, `llm/json/schema_binder.ex:130,152`, `validate.ex:107`, `type.ex:745`; and ~169 test lines mention `specification`/`get_json_schema`, ~252 mention `properties`.
4. Encoding: `Normandy.JSON.encode!` → `adapter.encode!(normalize(term))` (`json.ex`); `normalize` keeps any struct with its own `Jason.Encoder`. Tool definitions: `Toolset.to_tool_schemas/1` (`toolset.ex:244-254`) → `ClaudioAdapter.convert_tool_schema/1` (`claudio_adapter.ex:758-763`) → `Claudio.Messages.Request.add_tool/3` (map guard only, `request.ex:653`) → `Req json:` (Jason).
