## 0. Surprises

1. **Task 5.5's acceptance "a mid-turn compaction keeps the thinking block of the open tool call" contradicts the API's preserved-thinking rules as the skill documents them.** Normandy compacts by keeping a verbatim tail (keep-tail compaction). The skill says keep-tail compaction "fails on the retained turns: their thinking blocks were created with the full history present, so replaying them after the summary returns a 400 ... strip the thinking blocks from the retained turns" (`model-migration.md:1673`), and separately "never compact in the middle of a tool round (an assistant turn whose `tool_use` is still waiting on its `tool_result` goes back with its thinking intact)" (`preserved-thinking-migration.md:207`, `model-migration.md:1670`). So "keep the open round's thinking after a summary" = a 400 on enforced accounts (created on/after 2026-08-31, Opus 5.5 and Fable 5.1). The compatible fix is **not to compact mid tool round**, not to keep the thinking. The current strip (`window_manager.ex:409`, `summarizer.ex:407`) is the documented keep-tail recovery and is correct. AX-22's "Fix" line is wrong for 5.x models. Decision for Q (Q1).
2. **Compaction rewrites kept messages from their structs to wire blocks.** Both rebuilders add `msg.content` from `AgentMemory.history/1` (serialized), not `entry.content`: `window_manager.ex:400-414` (`rebuild_memory`) and `summarizer.ex:391-412`. After any compaction a kept `%ToolCallResponse{}` becomes a list of atom/string-keyed maps and a `%ToolResult{}` becomes `[%{type: "tool_result", ...}]`. A test pins it: `test/behaviours/compactor_test.exs:82` asserts `[%{type: "text", text: "answer"}] = result.memory.entries[last_id].content`. Consequences: `Turn.unanswered_tool_calls/1` (`turn.ex:359-378`, matches `%ToolResult{}` and reads `.tool_calls`) cannot see a kept batch any more; `drop_stale_thinking` loses `prefix_key`; the summarizer's next round sees mixed-key lists.
3. **Turn.Server never persists compaction** (`hooks/handlers.ex:67-69` says so; `server.ex:740-751` only swaps `config`; the store is append-only, `server.ex:1553-1564`). A rehydrated session (`server.ex:574-583`, `AgentMemory.from_entries/1`) replays the full, uncompacted history with all thinking. Requests sent after an in-memory compaction and requests sent after a rehydration therefore have different prefixes — the "deterministic function of the stored transcript" the skill requires for keep-tail (`preserved-thinking-migration.md:207`) does not hold. Not in the plan's Wave 5 text; flag for Q (Q5).
4. **"Byte-equal content blocks between the response and the next request" cannot be literal.** Claudio 0.7's canonical replay `Claudio.Messages.Response.to_assistant_content/1` (`deps/claudio/lib/claudio/messages/response.ex:447-451`) deliberately changes two shapes (probe, raw response block vs replayed):
   - `mcp_tool_result` loses `server_name` — intentional, "The API rejects `server_name` on a replayed mcp_tool_result" (`response.ex` `block_to_api(%{type: :mcp_tool_result})`, comment "probed 2026-09-26");
   - `text` loses `citations` — `block_to_api(%{type: :text, text: text})` emits only `type`/`text`. Not commented; likely a Claudio gap (Q3).
   - Before the last `fallback` block it applies the API's continuation rules (drops thinking/tool_use/text-adjacent blocks, keeps the `fallback` block itself).
   Every other probed type round-trips equal: `thinking`, `tool_use`, `mcp_tool_use`, `server_tool_use`, `web_search_tool_result`, `compaction`, and an unknown future type. Acceptance should be "equal to `Response.to_assistant_content(response)`", not to the raw HTTP body.
5. **AX-7 verified worse than reported in one way.** Probe with response `[thinking a, text(citations), tool_use t1, thinking b, text, tool_use t2, server_tool_use, web_search_tool_result]` → next request's assistant message was `[thinking a, thinking b, text "Let me check.\nAnd another.", tool_use t1, tool_use t2]`: thinking hoisted, texts merged with `"\n"`, citations, `server_tool_use` and `web_search_tool_result` dropped. The streaming path merges texts with `""` instead (`base_agent.ex:1297-1299`), so the two paths don't even rebuild the same bytes.
6. **AX-6 verified**: the same probe's second request had two consecutive `user` messages, one `tool_result` each. Claudio does not merge (`request.ex:169-174` appends).
7. **AX-9 verified, and the final answer is also garbled.** Probe transcript sent to the summarizer: `User: weather in Paris?` / `Assistant: [thinking]` / `Tool: ` / `Assistant: {"chat_message":"It is sunny."}` — tool result, assistant text, tool_use all empty; the final answer arrives as JSON (AX-21's shape). `max_tokens: 500` confirmed on the request.
8. **The summarizer's 500 can't be overridden by compaction.** `WindowManager.truncate_with_summary/2` calls `Summarizer.compress_conversation(client, agent, keep_recent: n)` with no `:max_tokens` (`window_manager.ex:346-350`), and `Compactor.WindowManager`'s opts schema has only `:context_window`, `:reserved_tokens`, `:strategy` (`behaviours/compactor/window_manager.ex:27-47`). The default is the only value compaction ever uses.
9. **The final assistant answer is never replayed as received** (out of AX-7's file list, but inside 5.3's "Assistant turns are replayed as received"): `turn.ex:164-166` appends the converted output-schema struct, which replays as `{"chat_message":...}` (`schema.ex:425`, AX-21), and its thinking is never stored. Whether 5.3 covers final answers is Q2.
10. **StreamProcessor drops server-tool input.** `input_json_delta` is accumulated only into `"tool_use"` blocks (`stream_processor.ex:174-183`), and `citations_delta` is ignored (`stream_processor.ex:112-131`). A streamed `server_tool_use`/`mcp_tool_use` keeps its `content_block_start` input (normally `{}`), so even a raw-block replay on the stream path would replay the wrong input until StreamProcessor learns those blocks.
11. Request-level coalescing (proposed below) breaks no existing test: every test client that inspects `request.messages` checks `role == "tool"` for presence or zero-count only (list in §1.4).

## Proposed approach

**AX-6 (smallest):** new pure `Normandy.Components.AgentMemory.request_messages/1` (or `Normandy.LLM.Request.coalesce_tool_results/1` over `[%Message{}]`) that turns each run of consecutive `"tool"` history messages into one `%Message{role: "tool", content: blocks1 ++ blocks2 ++ ...}`, order preserved. Use it at the three request builders: `base_agent.ex:250-263`, `base_agent.ex:1364-1370`, `token_counter.ex:184-195`. Leave `history/1`, the Turn core, the store (one entry per result) and `unanswered_tool_calls/1` untouched. Acceptance test: `ScriptedToolClient` with three calls + `StubClient`-style notify (or the Req.Test wire client) → second request has exactly one `"tool"` message whose list holds three `tool_result` blocks in call order; on the wire, one `user` message. No new options or telemetry.

**AX-3:** `extract_tool_uses/1` (`claudio_adapter.ex:972-1005`) keeps only `tool_use`; delete the `server__tool` rename. MCP/server blocks reach memory only through AX-7's raw blocks. Test: a Req.Test response with `mcp_tool_use` + `mcp_tool_result` + text, `stop_reason: end_turn` → no tool dispatched (`FakeTool` `notify:` sees nothing), final answer returned; a second turn's request replays both MCP blocks (without `server_name` on the result, Claudio's rule).

**AX-7:** add `ToolCallResponse` field `:content_blocks` (`{:array, :map}`, default `[]`): the API-shaped, string-keyed assistant content.
- Sync: in `populate_tool_call_response/3` set it from `Claudio.Messages.Response.to_assistant_content(claudio_response)` (Claudio already owns fallback continuation rules and MCP-result shaping).
- Stream: in `build_streaming_assistant_response/2` set it from the accumulated `content` (already string-keyed), after teaching `StreamProcessor` to accumulate `input_json_delta` for `server_tool_use`/`mcp_tool_use` and `citations_delta` (Surprise 10).
- `BaseIOSchema.to_json/1` for `ToolCallResponse`: when `content_blocks != []` return them (minus thinking blocks when `thinking == []`, so `drop_thinking`/`drop_stale_thinking` keep working); else the current rebuild (structs built by hand and pre-2.0 persisted structs, read with `Map.get(response, :content_blocks, [])`). A `tool_use` whose input is not an object keeps today's `%{}` substitution (only reachable after truncation, Task 5.2).
- `AgentMemory.drop_thinking/1` and `has_thinking?/1` cover `content_blocks`.
- Fix compaction's struct→wire rewrite (Surprise 2): rebuild from `entry.content` (`window_manager.ex:409`, `summarizer.ex:407`), update `compactor_test.exs:82`.
- Byte-equality test as in §3.6 against `to_assistant_content/1`; the live 400 check stays in Task 7.6.

**AX-9:** in `Summarizer.extract_content/1` normalize block keys (`Map.get(b, :type) || Map.get(b, "type")`), render `tool_use` as `Assistant called <name>(<json input>)`, `tool_result` as `Tool result (<name>): <content, capped>` (name from an id→name map built over the whole message list first), text as text, drop thinking. Unwrap a binary that decodes to `{"chat_message": s}` to `s`. Test with `RecordingClient`: a history with one tool round → the prompt contains the tool result's text and the assistant's text, no `[thinking]`.

**Summarizer budget:** default `max_tokens` = the agent's `max_tokens` (`Map.get(agent, :max_tokens)`, 16_000 after Task 1.3), falling back to 16_000 when the agent has none; doc says why (thinking shares the cap).
