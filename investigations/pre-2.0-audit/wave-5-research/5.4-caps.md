## 0. Surprises

1. **The `inspect/1` fallback SEC-3/AX-8 cite is gone.** `ToolResult`'s `format_tool_output/1`
   (`lib/normandy/components/tool_result.ex:45-51`) now calls `Normandy.JSON.encode!/1` with no
   rescue. Dispatch replaces an unencodable output with an error result before memory
   (`dispatch.ex:373-388` `wrap_output/2`, `dispatch.ex:263-273` `ensure_encodable/1`,
   `dispatch.ex:410-418` `unencodable_output/1`). Pinned by `test/json_struct_encoding_test.exs:65`
   (`"the tool ran, but its output cannot be sent as JSON: it contains a tuple"`). Unbounded
   `inspect/1` survives only in **error** text: `dispatch.ex:404` (`wrap_error/2`, a non-JSON error
   reason), `dispatch.ex:500` (budget denial reason), `lib/normandy/mcp/tool_wrapper.ex:111`,
   `lib/normandy/a2a/agent_tool.ex:159,257`. A cap applied to error results bounds all of them.
2. **No cap exists anywhere** (finding still true): `grep -rn "max_tool_result\|truncat" lib` hits
   only the memory tool's `Render` (`lib/normandy/tools/memory/render.ex:48`).
3. **Invalid UTF-8 binary outputs are not checked.** `ensure_encodable/1` passes any binary
   untouched (`dispatch.ex:264-266`, `when is_binary(output) or is_number(output)`), and so does
   `wrap_output/2` (`dispatch.ex:373-374`). Probe: `Jason.encode(<<255>>)` →
   `{:error, %Jason.EncodeError{message: "invalid byte 0xFF in <<255>>"}}`. A tool returning
   non-UTF-8 bytes therefore reaches memory and should fail every later request when it is
   encoded (end-to-end path through Claudio **not run**; PLAUSIBLE). Truncating with
   `String.slice/3` does not repair this (probe: `String.length(<<255, 97>>) == 2`, each
   invalid byte counts as a grapheme). `String.replace_invalid/2` is Elixir 1.16+, outside the
   `~> 1.15` constraint.
4. **One chokepoint covers every shell.** All three interpreters plus the sync and stream paths
   get tool results only from `Normandy.Agents.Dispatch` (section A.1). The cap goes into
   Dispatch alone, plus the two `Dispatch.ensure_encodable/1` calls in
   `lib/normandy/hooks/server_glue.ex:84,117`. No Turn core effect is needed, so the
   three-interpreter rule does not apply.
5. **`ensure_encodable/1` runs twice on the executed path**: once inside `answer/4`
   (`dispatch.ex:288` → `:252/:255`), then again after the after-hooks (`dispatch.ex:290-293`).
   A truncation that appends a note is **not idempotent** (the note pushes the text over the
   cap). So the cap must run once, at Dispatch's exits, not inside `answer/4`.
6. **The MemoryStore was never released.** `git ls-tree -r v1.0.0..v1.3.0` holds no
   `memory_store` file; `lib/normandy/behaviours/memory_store.ex` was added 2026-10-03 (`368c3ba`).
   So the behaviour callbacks, the Postgres migration and the Redis key layout can change in
   place with no upgrade path and no MIGRATING-2.0 entry. **But** the local test DB already ran
   `priv/test_repo/migrations/20261003000000_create_memory_store.exs` (it calls
   `Migration.up/0`). Changing `up/0` will not re-run it there. Before `mix test.postgres`
   locally, drop the test database (`MIX_ENV=test mix ecto.drop`), or add a second test
   migration. CI is unaffected: it starts a fresh `postgres:16-alpine` service each run
   (`.github/workflows/ci.yml:228-273`).
7. **The cap check reads only the first page, and is skipped when `max_namespace_bytes: nil`.**
   `others_bytes/3` (`commands.ex:398-409`) sums `store.list(ns, "/memories")`, which returns at
   most 1000 entries (`memory_store.ex:46`). The documented approximation
   (`lib/normandy/tools/memory.ex:21-27`, `docs/guides/agent-memory.md:211-216`) must be rewritten.
8. **Three memory tool tests pin the list-based cap and will become obsolete.** They are
   `test/tools/memory_test.exs` "nil disables the cap and lists nothing" (`:834`, uses
   `RecordingStore`), "a list failure during the cap check goes through the backend mapping"
   (`:843`, `CapListDownStore`) and "the cap is listed once for an edit even when it retries"
   (`:859`, `CountingStore`). See B.6.
9. **Postgres contract tests run in Sandbox shared mode on one connection**
   (`test/behaviours/memory_store/postgres_test.exs:10-18`, with a comment saying so). The
   "two concurrent writers, exactly one succeeds" case passes there because the two writes run
   one after the other. Real row-lock contention is not exercised. That is fine for the
   acceptance as written, but the test proves less on Postgres than on the other backends.
10. **Default `max_namespace_documents` (1000) equals `list_limit/0` (1000).** With defaults, a
    namespace never outgrows one list page, so the "listing stopped at 1000 files" note
    (`commands.ex:90-94`) fires only with `max_namespace_documents: nil` or a larger cap. The
    acceptance case "byte cap counting every document past 1000" therefore needs
    `max_namespace_documents: nil` (or > 1000) at the store level.

### A.6 Truncation semantics (probes)

```
s = String.duplicate("a", 99_999) <> "👨‍👩‍👧" <> "é"
{String.length(s), byte_size(s)}                          #=> {100001, 100019}
t = String.slice(s, 0, 100_000)
{String.length(t), byte_size(t), String.valid?(t), String.ends_with?(t, "👨‍👩‍👧")}
                                                         #=> {100000, 100017, true, true}
```

`String.length/1` and `String.slice/3` count graphemes, so the ZWJ family stays whole (Review
Focus #5). Cheap pre-check: `byte_size(text) <= cap` implies `String.length(text) <= cap`, so
most results skip the O(n) grapheme walk.

## Part B — Memory namespace caps (SEC-6/PERF-11, decision 12b)

### B.1 How namespace bytes are computed today

`lib/normandy/tools/memory/commands.ex`:

- `create/3` `:103-121`: `fits` (document bytes) → `not_directory` (a list at the path) →
  `not_under_file` (a get per ancestor) → `others_bytes(tool, loc, nil)` →
  `within_cap/4` → `store.put(ns, path, text, :any)`. That is four separate store round trips
  before the write: check-then-act.
- `edit/7` `:200-235` (used by `str_replace` `:123-138` and `insert` `:140-152`): get → transform
  → `fits` → `others_bytes` (listed once, carried through CAS retries; `others` param `:200`) →
  `within_cap` → `put(..., version)`, retried on `{:error, :conflict}` up to `max_cas_retries`.
- `others_bytes/3` `:398-409`: `nil` cap → `{:ok, 0}` (no list); else
  `store.list(ns, "/memories")`, reject the target path, and sum `size`. This is **the
  1000-document stop**: `list/3` returns at most `MemoryStore.list_limit()` = 1000
  (`lib/normandy/behaviours/memory_store.ex:46-50`).
- `within_cap/4` `:411-421` builds the error string, which three tests pin (B.6):
  `"Error: memory is full: writing #{path} would bring it to #{total} bytes; the limit is #{max}. Delete or shorten files first."`
- `rename/3` `:173-194`, `delete/3` `:154-163` and `delete_directory/2` `:165-171` do no cap check.
  Rename leaves bytes and count unchanged; deletes only shrink.
- Error type `:namespace_full` is already in the telemetry catalogue (`telemetry.ex:141-144`).
- Struct and validation: `lib/normandy/tools/memory.ex:41-49` (defstruct
  `max_namespace_bytes: 1_000_000`), `:51-60` (type), `:62-71` (`@options`), `:96-102` (check).
  **There is no `max_namespace_documents` yet.** The memory tool struct lives in the toolset, which
  is node-local, so ConfigTemplate needs no change for Part B.
- Bytes means **content bytes only** (`Docs.list/2` `size: byte_size(d.content)` `docs.ex:16`;
  Postgres `octet_length(content)` `postgres.ex:27`; Redis `HSTRLEN ... content` `redis.ex:52`).
  Paths are not counted.

### B.3 CAS writes per backend (exact)

**InMemory** (`in_memory.ex`). One `Agent` holds `%{ns => docs}`. `put/5` `:34-36` →
`update/3` `:50-55` = `Agent.get_and_update` running `Docs.put/4` on the namespace's docs map.
The write is serialized by the Agent.

**ETS** (`ets.ex`). A `:protected` table, one row `{ns, docs}`. `put/5` `:36-38` →
`GenServer.call(pid, {:apply, ns, :put, [path, content, expected]})`. `handle_call` `:61-65`
runs `apply(Docs, fun, [docs | args])`, then inserts or deletes the row. The write is serialized
by the owner GenServer; reads bypass it (`:31-34`).

**Mnesia** (`mnesia.ex`). One row `{table, ns, docs}`, attributes `[:namespace, :docs]`
(`:79`, pinned by `test/behaviours/memory_store/mnesia_test.exs` "create_tables/1" `:35` asserting
`:attributes == [:namespace, :docs]`). `put/5` `:94-96` → `update/3` `:112-118` =
`:mnesia.transaction` with `:mnesia.read(table, ns, :write)` (write lock on the namespace row,
`:120-125`), then `Docs.put/4`, then write or delete.

**Docs** (`docs.ex`, pure, shared by the three above). `put/4` `:27-34` does the CAS on the
whole namespace map; `write/4` `:71-74`. The whole namespace map is in hand inside the
serialized writer, so **exact bytes and count are computable atomically with no schema change**:
`map_size(docs)` and `Enum.sum(for {_, d} <- docs, do: byte_size(d.content))`. That is O(n)
per write, with n ≤ 1000 under the default cap.

**Postgres** (`postgres.ex`). Table `normandy_memory_documents`, PK `(namespace, path)`,
columns content, version and updated_at (`postgres/migration.ex:14-22`). Each write is a single
statement with **no transaction and no namespace-wide lock**:

- `put(:new)` `:60-65`: `INSERT ... VALUES ($1,$2,$3,1,$4) ON CONFLICT DO NOTHING`, then `num_rows` 1 or 0.
- `put(:any)` `:67-77`: `INSERT ... ON CONFLICT (namespace, path) DO UPDATE SET content = EXCLUDED.content, version = version + 1 ... RETURNING version`.
- `put(v)` `:79-89`: `UPDATE ... SET content = $3, version = version + 1, updated_at = $5 WHERE namespace = $1 AND path = $2 AND version = $4 RETURNING version`.
- `delete(:any)` `:91-100`; `delete(v)` `:102-118` (a CTE that tells conflict from missing);
  `delete_tree` `:120-127`; `delete_namespace` `:172-177`.
- `rename` `:129-170` is the only transaction (`repo.transaction`, `FOR UPDATE` on the moving
  rows ordered `COLLATE "C"`, unique-violation rescue → `{:error, :exists}`).
- `backend/1` `:226-230` rescues `DBConnection.ConnectionError` and `Postgrex.Error` into `{:error, e}`.

**Redis** (`redis.ex`). Per namespace, a sorted-set index `#{prefix}:mem:{#{b64(ns)}}:idx`
(`:226`) and a hash per document `#{prefix}:mem:{#{b64(ns)}}:doc:#{path}` (`:227,232`). The
hash tag `{...}` puts both in one cluster slot. Every write is one Lua script via `EVALSHA` with
an `EVAL` fallback on NOSCRIPT (`:208-220`):

- `@put` `:26-36`: `HGET version` → CAS on `ARGV[3]` (`new`/`any`/n) → `HSET content, version, updated_at` + `ZADD idx 0 path` → returns v or -1. Called with `KEYS = [idx, doc]` (`:172`).
- `@delete` `:38-45` (KEYS idx, doc); `@delete_tree` `:61-71` and `@rename` `:73-91` derive
  doc keys from `ARGV[1]` (the doc prefix), not from declared KEYS; `@delete_namespace` `:93-97`.
- The document count is already exact and O(1): `ZCARD idx`. **No byte counter exists.**

### B.4 What "bytes + count in the same CAS write" needs per backend

| Backend | Count | Bytes | Atomic with the CAS because | Schema / key change |
|---|---|---|---|---|
| InMemory | `map_size(docs)` | sum of `byte_size(content)` | Agent serializes | none |
| ETS | same | same | owner GenServer serializes | none |
| Mnesia | same | same | `:write` lock on the ns row in the transaction | none (keep `[:namespace, :docs]`) |
| Postgres | counter row | counter row | one transaction that locks the namespace's counter row `FOR UPDATE`, then CAS, cap check and counter update | **new table** in `Migration.up/0` (unreleased; Surprise 6), e.g. `normandy_memory_namespaces(namespace text PK, bytes bigint not null default 0, documents integer not null default 0)` |
| Redis | `ZCARD idx` | counter key | inside the Lua script | **new key** `#{prefix}:mem:{#{b64(ns)}}:bytes` (same hash tag), declared as `KEYS[3]` |

Postgres flow for `put` (every path, since the counters must always be maintained):

1. `INSERT INTO ns_table (namespace) VALUES ($1) ON CONFLICT DO NOTHING`
2. `SELECT bytes, documents FROM ns_table WHERE namespace = $1 FOR UPDATE`. This serializes
   every writer of the namespace.
3. `SELECT version, octet_length(content) FROM docs WHERE namespace = $1 AND path = $2`
4. CAS (`:new`, `:any` or `v` against the current version) → `{:error, :conflict}`
5. New totals: `bytes - old_len + octet_length($content)`; `documents + (existed ? 0 : 1)`.
   Over a limit → `{:error, {:namespace_full, ...}}` (rolls back).
6. Write the document, then `UPDATE ns_table SET bytes = ..., documents = ...`.

`delete`, `delete_tree` and `delete_namespace` take the same row lock and decrement in one
transaction (`delete_tree` can use `DELETE ... RETURNING octet_length(content)`). Rename leaves
the counters alone. Use `repo.query!` inside `repo.transaction` so a `Postgrex.Error` raises and
rolls back, and `backend/1` still maps it. The existing failure tests need that:
`postgres_test.exs` `MissingTableRepo` defines `transaction/1` as a real transaction and
expects `{:error, %Postgrex.Error{}}`; `ConnectionLostRepo.transaction/1` raises and expects
`{:error, %DBConnection.ConnectionError{}}`. The `RacingRepo` stub only intercepts
`query!("UPDATE" <> _, [ns, _from, to, _moving])`, which is rename's 4-param UPDATE. A counter
`UPDATE` with 4 params would match too, but only `rename` runs under `RacingRepo`, and rename
does not touch the counters.

Alternative without a table: `pg_advisory_xact_lock(hashtextextended($1, 0))`, then
`SELECT coalesce(sum(octet_length(content)), 0), count(*) ... WHERE namespace = $1` in the
transaction. This is exact and race-free, with no schema change, but O(n) per write (a
PK-prefix scan; `octet_length` on toasted text reads the header only). It "computes" rather
than "tracks", which departs from decision 12b's wording.

Redis `@put` sketch (KEYS idx, doc, bytes):

```lua
local cur = redis.call('HGET', KEYS[2], 'version')
-- existing CAS checks (return -1)
local old = 0
if cur then old = redis.call('HSTRLEN', KEYS[2], 'content') end
local bytes = tonumber(redis.call('GET', KEYS[3]) or '0') - old + string.len(ARGV[2])
local docs = redis.call('ZCARD', KEYS[1]); if not cur then docs = docs + 1 end
if ARGV[5] ~= '' and bytes > tonumber(ARGV[5]) then return {-2, bytes} end
if ARGV[6] ~= '' and docs  > tonumber(ARGV[6]) then return {-3, docs}  end
-- HSET, ZADD as today; then:
redis.call('SET', KEYS[3], bytes)
return v
```

Lua `string.len` counts bytes. `@delete` subtracts `HSTRLEN` before `DEL` (`DECRBY`).
`@delete_tree` sums `HSTRLEN` inside its loop. `@delete_namespace` adds `DEL bytes`. `@rename`
is unchanged. Redis tests that would see the new key: `redis_test.exs` "a rename racing a
write leaves no orphaned document hash" scans `tag <> ":doc:*"`, so `:bytes` does not match and
the test is unaffected. `delete_prefix/1` scans `prefix <> "*"`, so it cleans the new key.

## Proposed approach

### P-A. Tool result cap

1. `BaseAgentConfig`: `field(:max_tool_result_chars, :any, default: 100_000)`, plus
   `@spec default_max_tool_result_chars() :: pos_integer()`.
2. `InitOptions`: `max_tool_result_chars: [type: {:or, [:pos_integer, nil]}, default: BaseAgentConfig.default_max_tool_result_chars(), type_doc: "`t:pos_integer/0` or `nil`", doc: "Longest tool result, in characters (graphemes), the model sees; a longer one is cut and ends with a note. `nil` = no cap. A tool's `Toolset.register/3` `:max_result_chars` overrides it."]`.
   Set it in `BaseAgent.init/1` (`base_agent.ex:79-104`).
3. `Toolset`: a new field `result_caps: %{String.t() => pos_integer() | nil}`; register option
   `max_result_chars: [type: {:or, [:pos_integer, nil]}, doc: ...]` (no default). Store it on
   `{:ok, v}` and delete it on `:error`, like `timeouts`. Add
   `@spec max_result_chars(t(), String.t()) :: {:ok, pos_integer() | nil} | :error`. Update
   `unregister/2` and both `filter_by_*` functions, plus the doctest text.
4. `Dispatch`: a new `@doc false def finish(config, call, %ToolResult{} = r)`, which runs
   `ensure_encodable/1` and then `cap/3`. Apply it at every exit listed in A.1 (`:185`,
   `:293`, `:297`, `:314`, `:315`, `:354`). `answer/4` keeps only the after_tool slot and
   encodability. `cap/3`:
   - limit = `Toolset.max_result_chars(toolset, call.name)` → on `:error`, the agent cap
     `Map.get(config, :max_tool_result_chars, default)`; `nil` → result unchanged;
   - text = the same rendering `format_tool_output/1` uses (binary as-is, number via
     `to_string`, else `Normandy.JSON.encode!/1`, which is safe after `ensure_encodable/1`).
     Expose it once, e.g. `ToolResult.render_output/1`, and call it from both places;
   - `byte_size(text) <= limit` → unchanged (fast path). Else `m = String.length(text)`; when
     `m > limit`, set `output: String.slice(text, 0, limit) <> "\n[truncated: #{limit} of #{m} chars shown]"`,
     keep `is_error`, and emit the event.
   - `ServerGlue` (`server_glue.ex:84,117`) switches from `Dispatch.ensure_encodable/1` to
     `Dispatch.finish/3` (it has config and call).
5. Telemetry: `[:normandy, :tool, :result_truncated]`, measurements
   `%{original_chars: m, kept_chars: limit}`, metadata via a new
   `Metadata.tool_result_truncated(config, call, source)` with `tool_name`, `agent_name`,
   `tool_call_id`, the ids, and `limit_source: :agent | :tool`. Document it under
   `## Events` in `telemetry.ex`.
6. ConfigTemplate: add `:max_tool_result_chars` to `@data_fields`.
7. Error-text hygiene (optional, small): `dispatch.ex:404` and `:500`
   `inspect(x, limit: 50, printable_limit: 2_000)`. The cap already bounds them, but bounded
   inspects avoid building megabyte strings first.
8. Tests: a `ReturnTool` support module; Dispatch unit tests (agent cap; per-tool cap
   overriding the agent; per-tool `nil` turning off an agent cap; agent `nil`; a map output
   truncated as JSON text; an error result truncated; the event and its measurements); Review
   Focus #5 (text of `limit - 1` ASCII chars + a ZWJ family + a multibyte tail →
   `String.valid?`, ends with the whole family + note, `String.length` before the note ==
   limit); a `run/2` test with `ScriptedToolClient` asserting memory holds the truncated
   result; a `stream/3` test asserting the `:tool_result` StreamEvent carries the truncated
   result; a Turn.Server test (one fresh batch); ConfigTemplate round trip + "template without
   the field rebuilds with 100_000"; an `init/1` option validation test.

### P-B. Memory caps

1. Behaviour: replace `put/5` with
   `@callback put(handle, ns, path, content, version | :new | :any, limits) :: {:ok, version} | {:error, :conflict} | {:error, {:namespace_full, :bytes | :documents, non_neg_integer()}} | {:error, term}`
   where `limits :: [max_bytes: pos_integer() | nil, max_documents: pos_integer() | nil]`
   (keyword; a missing key = no limit). Each of the 5 backends defines
   `def put(h, ns, path, content, expected, limits \\ [])`, which exports `put/5` too, so the 53
   test call sites and the 1001-document contract test keep working. The 9 stubs in
   `test/support/memory_stub_stores.ex` change `put/5` to `put/6`. Add to the moduledoc: "a
   `put` that would make the namespace's total content bytes exceed `:max_bytes`, or its
   document count exceed `:max_documents`, writes nothing and returns
   `{:error, {:namespace_full, which, would_be}}`; the check and the write are one atomic step."
   Docs about which one wins when both are exceeded: check bytes first.
2. `Docs.put/5` (pure) gets `limits` and computes the totals from the map. InMemory, ETS and
   Mnesia pass `limits` through (`in_memory.ex:35-36`, `ets.ex:37-38` + `handle_call` args,
   `mnesia.ex:95-96`).
3. Postgres: add `normandy_memory_namespaces` to `Migration.up/0` and `down/0`. `put`,
   `delete`, `delete_tree` and `delete_namespace` become one transaction each, as in B.4. Note in
   the moduledoc that direct SQL writes to the documents table bypass the counters.
4. Redis: `KEYS[3]` bytes key in put, delete and delete_tree; `DEL` in delete_namespace; limits
   as `ARGV[5]`, `ARGV[6]` (`''` = none); new return codes `{-2, bytes}`, `{-3, docs}`. Note: the
   `@put` return type becomes "integer or array"; Redix decodes both.
5. Tool: `Memory` gets `max_namespace_documents: 1000` (`pos_integer | nil`) in defstruct,
   type, `@options` and validation (copy the `max_namespace_bytes` check, `memory.ex:96-102`).
   `Commands.create/3` and `edit/7` pass
   `[max_bytes: tool.max_namespace_bytes, max_documents: tool.max_namespace_documents]` on `put`.
   Delete `others_bytes/3` and `within_cap/4`, and the `others` parameter of `edit/7`. Map
   `{:error, {:namespace_full, :bytes, total}}` to today's exact text (keeps 4 tests) and
   `{:error, {:namespace_full, :documents, n}}` to e.g.
   `"Error: memory is full: creating #{path} would make #{n} files; the limit is #{max}. Delete files first."`
   (error type `:namespace_full` for both). A CAS conflict retry re-runs the store's check, so
   no cached total.
6. Contract (`memory_store_contract.ex`), new store-level cases:
   - (a) bytes counted past the list page: 1001 one-byte documents with
     `max_documents: nil`, then a `put` with `max_bytes: 1001` of a new 1-byte document →
     `{:error, {:namespace_full, :bytes, 1002}}`, and one with `max_bytes: 1002` → ok;
   - (b) the count cap: `max_documents: 3`, a fourth new path is refused
     (`{:namespace_full, :documents, 4}`), an overwrite of an existing path is allowed;
   - (c) replacing a document counts its old size once;
   - (d) two concurrent `put`s of different new paths, each fitting alone and over the cap
     together → exactly one `{:ok, _}` and one `{:error, {:namespace_full, :bytes, _}}`;
   - (e) counters follow `delete`, `delete_tree`, `rename` and `delete_namespace` (delete
     frees room for a later put).

   Tool-level: rewrite the three obsolete memory_test cases (B.6) and add a
   `max_namespace_documents` create refusal.
7. Docs: memory moduledoc, `docs/guides/agent-memory.md` limits table (drop "approximate"),
   CLAUDE.md memory bullet (with Q's approval, per earlier practice).
8. Gate: `mix precommit`; `docker start normandy-test-pg`, `MIX_ENV=test mix ecto.drop`,
   `POSTGRES_PORT=55432 mix test.postgres`; `mix test.redis`; stop the container afterwards.

## Questions for Q

1. **Does the cap apply to `is_error` results?** Options: (a) yes, every result the model sees;
   (b) only successful outputs. Recommend (a): error text is where the unbounded `inspect/1`s
   live (Surprise 1). If wrong: a huge error string still fills the context.
2. **Do the hooks see the full output?** Options: (a) cap last, after `after_tool` and the
   after-hooks (hooks see the full output; the StreamEvent and memory get the capped one);
   (b) cap before the hooks. Recommend (a): a hook can summarize a big result itself before the
   blunt cut. If wrong: a hook that logs results logs megabytes (it already does today).
3. **Map and list outputs**: truncate the encoded JSON text (the output becomes a string that is
   cut-off JSON plus the note) vs. turn an oversize structured output into an error result.
   Recommend truncation (decision 12a says truncate; the note tells the model). Cost if wrong:
   the model may try to parse broken JSON. The note should say so: e.g.
   `[truncated: N of M chars shown]` is decision text, so keep it verbatim.
4. **Invalid UTF-8 binary output** (Surprise 3): (a) make it an error result in
   `ensure_encodable/1` ("the tool ran, but its output is not valid UTF-8"); (b) scrub invalid
   bytes (no `String.replace_invalid/2` on 1.15; hand-rolled); (c) leave it out of 5.4.
   Recommend (a), in 5.4: same pattern as the unencodable-term case, a few lines, and the cap
   test touches this code anyway. If not fixed: a session can wedge on a later request.
5. **Per-tool option name**: `Toolset.register/3` `:max_result_chars` (scoped by the call) vs.
   the agent's name `:max_tool_result_chars`. Recommend `:max_result_chars`, documented next to
   `:timeout`. Cheap either way.
6. **"chars" = graphemes** (`String.length/1`), which is what "grapheme boundary" implies, vs.
   codepoints. Recommend graphemes, plus the `byte_size` fast path. Cost: an O(n) walk only on
   results whose byte size exceeds the cap.
7. **Store API shape**: (a) `put/6` with a `limits` keyword (impls default `\\ []`); (b) keep
   `put/5` and add a separate `put_capped/6` callback; (c) pass limits through the handle.
   Recommend (a): one write path, so no backend can forget the counters. Cost: 9 stub modules
   edited.
8. **Postgres**: counter table (tracks, O(1), schema change in the unreleased migration) vs.
   advisory lock + `SUM`/`count` (computes, O(n), no schema). Recommend the counter table,
   matching decision 12b's "track". Cost if wrong: one more table to document, and counters
   drift if a host writes rows directly (document it).
9. **A write that shrinks a namespace already over the cap** (for example after the host lowered
   it): today it is refused if the new total > cap (`commands.ex:416`). Options: keep strict, or
   allow any write that does not increase bytes or count. Recommend allowing it, so a model can
   repair an over-full namespace by shortening files. Cost if wrong: an over-cap namespace can
   only be fixed by deletes.
10. **`max_namespace_documents` when the caller passes `max_namespace_bytes: nil`**: independent
    caps (each `nil`-able). Recommend independent, both default on. No real cost.
