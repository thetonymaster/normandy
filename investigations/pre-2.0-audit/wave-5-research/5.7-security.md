## 0. Surprises

1. **SEC-2: nothing gives a "server name" to default the prefix to.** `Claudio.MCP.Client`'s
   callbacks are `list_tools/2`, `call_tool/4`, `list_resources/2`, `read_resource/3`,
   `list_prompts/2`, `get_prompt/4` and `ping/2` (`deps/claudio/lib/claudio/mcp/client.ex:71-96`).
   None of them returns server info, and the client is an opaque term (a pid, or
   `{module, client}` for Hermes). So plan.md's "prefix by default" can't be built as written.
   Even if we could read `serverInfo.name`, it would be **chosen by the server**, which is the
   party SEC-2 distrusts. The prefix has to come from the host: either make `:prefix` required,
   or require an explicit opt-out. See Q1.
2. **SEC-2: a default prefix can quietly loosen policy on upgrade.** Ruleset rules are kept in
   the persisted template (`behaviours_refs.policy`, `config_template.ex:113`) and matched on the
   tool name (`policy_engine.ex:141-149`). Take a host whose `default_action: :allow` comes with
   a `%{match: "delete_*", action: :deny}` rule. After the upgrade its MCP tool is called
   `srv__delete_x`, the rule no longer matches, and the call is **allowed**. A host with a
   restrictive default instead finds its allow rules stop matching, so things get stricter.
   MIGRATING needs a loud entry for this, and requiring an explicit `:prefix` makes the host
   see it.
3. **SEC-2: the `__` delimiter is ambiguous unless the prefix is constrained.** With prefix
   `"a_"` and tool `"b"`, and with prefix `"a"` and tool `"_b"`, both give `"a___b"`. A rule
   `"a___*"` then also matches the other server's tools. `AgentTool.sanitize_name/1` already
   collapses `_+` and trims `_` at both ends (`a2a/agent_tool.ex:131-139`), so A2A names never
   collide this way. The MCP prefix needs the same kind of rule: no `__` inside it and no `_` at
   either end.
4. **SEC-2: ToolWrapper struct literals skip `new/4`.** The moduledoc example builds
   `%ToolWrapper{adapter:, client:, tool:, prefix:}` directly (`tool_wrapper.ex:20-25`), and
   `name/1` returns the bare name when the prefix is `nil` (`tool_wrapper.ex:94`). Making
   `:prefix` required in `new/4` alone leaves that route open. Use `@enforce_keys [:prefix]`, or
   have `name/1` raise on `nil`.
5. **SEC-4 is confirmed and broader than reported.** Probe, `SemanticScope` with
   `on_error: :open` and then `:closed`: a classifier that `exit(:timeout)`s gives
   `{:caught, :exit, :timeout}`, a `KeyError` gives `{:raised, KeyError}` and a `throw` gives
   `{:caught, :throw, :nope}`. All six combinations escape `Guardrails.run/3`. Guardrails also
   have **no timeout of their own**: "timeouts" in plan.md can only mean an exit *raised inside*
   the guard (for example a `GenServer.call` timeout). A guard that just blocks hangs the turn.
   A real guard timeout is a new feature (Q3). Also, `SemanticScope` takes **functions** as
   opts, and `ConfigTemplate.from_config/2` refuses functions in `guardrails`
   (`config_template.ex:134-147`, pinned by `config_template_test.exs:381-391`). So
   `SemanticScope` can't be used under `Turn.Session` at all. Its realistic callers are
   `BaseAgent.run`/`stream`/`admit` and `AgentProcess` in `:inline` mode.
6. **SEC-8: signing only the template, or only checking it in `rebuild/3`, is too late and too
   narrow.** `Turn.Server` reads the unverified template **before** `rebuild/3` runs. It takes
   `template_id` (which picks the node-local supplement, and so the **toolset**,
   `server.ex:561,627`), `behaviours_refs.credential` (it **calls `cred_mod.get_token/2` with
   template-chosen opts**, `server.ex:562-565`), `resume_policy` (`server.ex:465-469`) and
   `server_options` (`server.ex:600-614`). Someone with write access to the store can therefore
   point a session at another template's toolset, or at another credential, without touching
   anything `rebuild/3` checks. The same store also holds turn state (parked calls with their
   input) and history, decoded by the same `Codec`. Neither a template MAC nor a template
   plain-data check covers those.
7. **SEC-8: `[:safe]` decoding does let closures through (probe).** I encoded
   `%{tool_context: %{cb: fn x -> {x, secret} end}}`, decoded it with
   `binary_to_term(_, [:safe])`, called it, and got `{1, "S"}`. Only Postgres and Redis decode
   bytes (`session_store/postgres.ex:259-260`, `session_store/redis.ex:326-327`). InMemory, ETS
   and Mnesia keep native terms, and anyone who can write those is already a cluster node.
8. **SEC-7 is confirmed (probe).** Setup: a mount `"/memories/org" => {"acme/kb", :read_only}`.
   Writing `/memories/org/policy.md` from `"acme/u"` is refused (read-only). Running `create
   /memories/policy.md "EVIL"` with session namespace `"acme/kb"` returns `{:ok, ...}`, and then
   `view /memories/org/policy.md` from `"acme/u"` shows `EVIL`.
9. **SEC-9: the A2A server is not a Plug and never reads a body.** `handle_message/2,3` takes an
   already decoded `%Claudio.A2A.Message{}` (`a2a/server.ex:127-165`), so the HTTP body limit
   is the host's (for example `Plug.Parsers :length`). The third positional argument of
   `handle_message/3` is the trace **carrier** (`[{String.t(), String.t()}]`), not an opts list.
   New options therefore need `handle_message/4`. A host can *already* scope tools per caller by
   passing `%{config | tool_context: ...}`, so the `:tool_context` option is convenience plus
   documentation, not a new capability (Q5).
10. **Some LOW findings have moved since the audit.**
    - **SEC-15 is half fixed.** A missing tool at approval time now gets `not_found_result`
      through `Dispatch.execute_approved/3` (`dispatch.ex:300-317`); the `MatchError` and the
      `Tools.Registry` named in the finding no longer exist. The optional tool fingerprint is
      not built.
    - **SEC-17 is mostly fixed.** `execute/3`, `execute_parallel/3` and `execute_sequential/3`
      were removed in Wave 3 (MIGRATING-2.0.md:657). `Executor.execute_tool/2` and
      `execute_tool_classified/2` are still public and still skip policy, hooks and budget. The
      moduledoc doesn't say so (`executor.ex:1-16`).
    - **SEC-14 overlaps Wave 6.** plan.md Task 6.5 already lists "supervised `run_async`
      limits". Both `Task.start` sites are still there (`coordination/agent_process.ex:626,658`).
    - **SEC-13 is narrower than reported.** A `}` inside the session id leaves stream and meta
      with the **same** tag, because both keys share the prefix up to the id. Only an id that
      starts with `}`, or the empty id `""`, gives an empty tag `{}`. The whole key is then
      hashed, and stream and meta can land in different slots.
11. **A2A AgentTool names are chosen by the remote too:** `"a2a__" <> sanitize(card.name)`
    (`a2a/agent_tool.ex:206-211`). This is the same class as SEC-2 for A2A, and it isn't in
    plan.md. A remote whose card is named `read_and_purge` gets `a2a__read_and_purge`, which
    matches `"a2a__read*"`. Mentioned for Q (Q2); not inventoried further.

## SEC-2. MCP tool names: prefix by default

### Current behaviour
- `tool_wrapper.ex:54`: `defstruct [:adapter, :client, :tool, :prefix]`, with no
  `@enforce_keys`.
- `tool_wrapper.ex:56-61`: the `:prefix` option is `type: :string`, optional, with no default.
- `tool_wrapper.ex:82-91`: `new/4` sets `prefix: Keyword.get(opts, :prefix)`, so the prefix is
  `nil` by default.
- `tool_wrapper.ex:94-95`:
  ```elixir
  def name(%__MODULE__{tool: tool, prefix: nil}), do: tool.name
  def name(%__MODULE__{tool: tool, prefix: prefix}), do: "#{prefix}__#{tool.name}"
  ```
- `tool_wrapper.ex:108-109`: `run/2` calls `adapter.call_tool(client, tool.name, ...)` with the
  **unprefixed** name. That is correct and doesn't change.
- `mcp/registry.ex:27,31`: the Registry options *are* ToolWrapper's schema (one source).
  `BaseAgent.register_mcp_tools/4` (`base_agent.ex:2096-2108`) uses the same schema through
  `Registry.__opts_schema__(:discover_and_register)`. Changing the schema in `tool_wrapper.ex`
  therefore changes all four entry points: `ToolWrapper.new/4`,
  `Registry.discover_and_register/4`, `Registry.wrap_tools/4` and
  `BaseAgent.register_mcp_tools/4`.
- `mcp/registry.ex:75-85`: `register_all/2` halts on the **first** invalid or taken name, with
  `{:error, {:invalid_tool_name, name}}` or `{:error, {:tool_name_taken, name}}`, so no tool of
  that server is registered.
- `toolset.ex:490-492`: `valid_name?/1` is `~r/\A[a-zA-Z0-9_-]{1,64}\z/`, the same as
  Anthropic's `^[a-zA-Z0-9_-]{1,64}$`.
- `policy_engine.ex:141-149`: `Ruleset` matches globs on the name only. A trailing `*` means a
  prefix match (`String.trim_trailing(pattern, "*")` trims every trailing `*`).

### How the prefix interacts with other things
- **Name limits.** The prefixed name is `prefix <> "__" <> tool`, so a tool name can be at most
  `62 - byte_size(prefix)` bytes. A server tool longer than that, or with a character outside
  `[a-zA-Z0-9_-]` (for example `files.read`), fails registration of the whole server, as it does
  today for dotted names (`registry_test.exs:140-148`). I believe the current MCP spec allows `.`
  in tool names; this is unverified against the spec text today. A prefix itself should satisfy
  `~r/\A[a-zA-Z0-9-]+(?:_[a-zA-Z0-9-]+)*\z/` (no `__`, no leading or trailing `_`) and be at
  most 61 bytes. Then the first `__` in a name always ends the prefix, so `"srv__*"` matches
  exactly server `srv`'s tools (and any local tool the host chose to name `srv__...`).
- **Existing policy globs.** These are persisted in the template (`behaviours_refs.policy`,
  `config_template.ex:113`). They are not rewritten, and Normandy can't know which rules were
  aimed at MCP names. See Surprise 2: whether the upgrade loosens or tightens policy depends on
  `default_action`.
- **Persisted templates.** The toolset is *not* in the template. It comes from the node-local
  supplement (`config_template.ex:206`, `supplement_toolset!/1` at `:313-339`), so templates
  need no translation. What *is* persisted with names:
  - (a) Policy globs (above).
  - (b) History: `tool_use` blocks carry the old unprefixed name, and replay sends them with
    `tools` listing only prefixed names. I don't know whether the API rejects a history
    `tool_use` whose name is missing from `tools`. **Unverified.** Task 7.6's live run could
    probe it. Task 5.2's "tools withheld at the iteration cap" raises the same question.
  - (c) Parked approvals. `Turn.State` holds `call.name`. After the upgrade
    `Dispatch.execute_approved/3` finds no tool and answers `not_found_result`
    (`dispatch.ex:300-317`). That degrades cleanly.
  - (d) `A2A.Server.build_agent_card(expose_tools: [...])` names and any host hook matching
    `call.name`: a stale name stops matching (fail-closed for `expose_tools`).

### Call sites (grep)
`grep -rn "ToolWrapper.new(\|discover_and_register(\|wrap_tools(\|register_mcp_tools(" test e2e lib | grep -v prefix`
gives 18 test sites without a prefix:

example at `lib/normandy/mcp/tool_wrapper.ex:20`. `e2e/12_mcp_a2a.exs:66` already passes
`prefix: "city"`.

### Tests that pin today's behaviour

- `test/mcp/tool_wrapper_test.exs:70`: "tool_name without prefix".

## SEC-8. Template integrity

### Current behaviour
- `config_template.ex:180-215`: `rebuild/3`. Only `hooks` are re-validated
  (`:183`, `Hooks.validate_entries!(…, load: false)`, which includes the plain-data check at
  `hooks.ex:245-255`). `behaviours_refs` `policy`, `budget`, `credential`, `compactor` and
  `model_catalog` are taken as they are (`:185-191`). `@data_fields` (`:51-59`, which include
  `guardrails` and `tool_context`) are merged by `struct/2` (`:211`) with no `unstorable?`
  check.
- `config_template.ex:134-158`: `unstorable?/1` (functions and pids only) runs in
  `from_config/2` only. The other helper, `Hooks.plain_data?/1` (`hooks.ex:245-255`), also
  refuses references and ports, so the two disagree.
- The template is read before `rebuild/3` (Surprise 6): `server.ex:441-454` (`start_config`),
  `:542-548` (load), `:560-570` (`reconstruct_config`: `template_id` picks the supplement, the
  credential module and opts are **called**), `:465-469` (`resume_policy`), `:600-614`
  (`server_options`). `Turn.Session.server_opts/1` loads it only to check it exists
  (`session.ex:345-349`).
- `session_store/codec.ex:17-24`: `binary_to_term(bin, [:safe])`, retried once after loading
  every application module. Closures decode (Surprise 7).
- What an attacker with write access to the store controls on the next rehydrate:
  - the policy (for example `PolicyEngine.AllowAll`);
  - the guardrails (cleared);
  - the hooks (removed);
  - `tool_context` (another tenant's `memory_namespace`);
  - the credential ref (another key, chosen by its opts);
  - `template_id` (another supplement and its toolset);
  - `server_options` (for example `on_approval_timeout: :continue`);
  - turn state (the input of a parked call, after a human saw a different one);
  - history (injected messages).
- Docs: `docs/guides/distributed_sessions.md:47,109-112` calls the template "non-secret" and
  never says the store is a trust boundary.

### Option A: document the trust boundary
- **What it is.** A "Trust boundary" section in `ConfigTemplate`'s moduledoc and in
  `distributed_sessions.md` stating:
  - write access to the session store is equivalent to code-level control of authorization;
  - the list above;
  - Postgres and Redis must be single-tenant, or ACL'd, for Normandy's role;
  - MIGRATING says nothing changed.
- **Cost:** about 1 hour, no code, no test beyond a doc check. **Protects nothing.**

### Option C: plain-data and behaviour check on load (no keys)
- **What it is.** One check, `ConfigTemplate.check_loaded!/1`, called in `Turn.Server` straight
  after `load_config_template` (`server.ex:449`, before `reconstruct_config`), and again inside
  `rebuild/3` for direct callers. It:
  1. refuses any function, pid, reference or port anywhere in the template, using one shared
     `plain_data?/1` (fold `unstorable?/1` into `Hooks.plain_data?/1`'s stricter rule);
  2. requires each `behaviours_refs` slot to be `{module, keyword}` whose module, once loaded,
     declares the matching behaviour (`PolicyEngine`, `Budget`, `CredentialProvider`,
     `Compactor`, `ModelCatalog`), and each guard module to declare `Normandy.Guardrails.Guard`;
  3. optionally, a supplement key `:pinned` (for example `[:policy, :guardrails, :credential]`)
     whose values come **from the supplement** and must equal the template's. A mismatch raises
     `ArgumentError` naming the field. This is the trusted, node-local half pinning the
     security controls, with no secret needed.
- **Cost:** about 0.5-1 day, roughly 60-100 lines plus tests (a closure in `tool_context`, a pid
  in guardrails, a non-behaviour module in policy, a pinned mismatch). Nothing changes for 1.x
  templates: they already contain only plain data and real behaviour modules (verify with the
  existing 1.x fixture, `config_template_test.exs:393-405`).
- **Protects against:** closures and type confusion; swapped policy, guardrails or credential
  when pinned.
- **Doesn't protect:** `tool_context` values (per-session data, can't be pinned), `template_id`
  (it *is* the supplement key), turn state, history.

### Option B: HMAC-signed templates
- **Key config.** The template provider (node-local) supplies a keyring. Either a new optional
  `AgentTemplate` callback `signing_keys(handle) :: [{key_id :: String.t(), key :: binary()}]`,
  or a `Turn.Session.new/1` / `Turn.Server` option `template_keys: {mod, fun, args}` so the
  secret is fetched at use and never sits in a stored struct. The first key signs and every key
  verifies, which allows rotation. It is never stored in the template or in `config :normandy`
  (to keep it out of `Application.get_env` dumps).
- **What gets MAC'd.** The exact bytes, not a canonical re-encoding: `term_to_binary` is not
  guaranteed stable across OTP releases, and CI runs OTP 26/27. `from_config` returns an
  envelope `%{template_id: id, v: 2, key_id: kid, payload: bin, mac: mac}`, where
  `bin = :erlang.term_to_binary(template_map)` and
  `mac = :crypto.mac(:hmac, :sha256, key, [kid, 0, bin])` (OTP 26+, so `:crypto.mac/4` and
  `:crypto.hash_equals/2` are available). The stores keep the envelope as an opaque term, with
  no backend change. Verification is `hash_equals`, then `binary_to_term(bin, [:safe])`, then
  Option C's checks.
- **Where it is verified.** In `Turn.Server.start_config/3`, before `reconstruct_config/2`
  (`server.ex:449-450`), because `template_id`, the credential ref and `server_options` are read
  there. `rebuild/3` accepts only a verified, unwrapped map. A new
  `ConfigTemplate.open!(envelope, keys)` does both steps.
- **1.x templates.** These are unsigned maps. Once keys are configured, an unsigned template is
  refused (`ArgumentError` naming the template and the migration step) unless the host sets
  `unsigned_templates: :accept` for a migration window. With that set, the template is
  re-saved signed on the next successful `Turn.Session.run`. That re-save is trust on first use,
  which MIGRATING must say. Without keys, behaviour is unchanged and templates are unsigned.
  Review Focus #1 (1.x rebuild) still holds.
- **Cost:** about 2-3 days:
  - the envelope format and its translation;
  - the keyring option and docs;
  - Session save and Server load paths;
  - the rotation, refusal and migration-window tests;
  - a MIGRATING section;
  - the risk of a rolling deploy where nodes have different keys.
- **Protects against:** template tampering only. Turn state and history stay unprotected unless
  the same envelope wraps `save_turn_state` and the history entries. That doubles the cost and
  touches the store contract and all five backends.

### Recommendation
**A + C now. B is deferred, recorded as a known limit.** C closes the "closure in a guard opt"
and type-confusion cases and, with `:pinned`, lets a host lock policy, guardrails and the
credential to node-local values, without key management or a format change. A states plainly
that the store is trusted (as trusted as code) and lists what a store writer controls,
including turn state and history, which B wouldn't cover either. **If Q is wrong** and a host
runs a shared, multi-writer store, an attacker can still change `tool_context`, `template_id`
or history. B would close only the first two. (Q4)

## SEC-9. A2A server: request size and per-caller `tool_context`

### Inventory

## Proposed approach

**SEC-2**
- Make `:prefix` required in `ToolWrapper.new/4`'s schema (`tool_wrapper.ex:56-61`). That one
  change covers all four entry points.
- Type: `{:or, [{:custom, __MODULE__, :prefix, []}, {:in, [false]}]}`. The custom validator
  enforces `~r/\A[a-zA-Z0-9-]+(?:_[a-zA-Z0-9-]+)*\z/` and ≤ 61 bytes. `prefix: false` is the
  explicit opt-out: the bare server name, with a docs warning.
- Add `@enforce_keys [:adapter, :client, :tool, :prefix]`. `name/1`: `false` gives `tool.name`,
  a binary gives `prefix <> "__" <> tool.name`.
- Docs: in the ToolWrapper and Registry moduledocs, and in `PolicyEngine.Ruleset`'s docs, say
  that rules match names a server chose, and to write `"srv__*"`.
- MIGRATING: the policy-glob hazard (Surprise 2), plus `expose_tools` and hook name matching.
- Tests:
  - a missing `:prefix` raises `ArgumentError` naming it (all four entry points, extend
    `integration_options_test.exs`);
  - `prefix: "a_"` and `"a__b"` are refused;
  - the attack itself: a server tool `read_and_purge` registered with `prefix: "srv"` does not
    match `%{match: "read_*", action: :allow}` and gets `default_action: :require_approval`
    (`Ruleset.check/2` directly).

**SEC-4**
- In `invoke/4`, add these clauses, routed to `on_error_result/3`:
  ```elixir
  catch
    :exit, reason -> on_error_result(policy, mod, {:exit, reason})
    :throw, value -> on_error_result(policy, mod, {:throw, value})
  ```
  Under `:closed` the message names the kind and the exit tag only, like
  `Executor.describe_reason/1`.
- Separate host code from builtin configuration:
  - Add `Normandy.Guardrails.GuardError` (public exception, fields `kind` and `reason`, message
    module or tag only).
  - `SemanticScope` calls `classifier` and `fast_path` through a private `call_host/3` that
    catches raise, exit and throw and raises `GuardError`. `GuardError` is neither
    `ArgumentError` nor `KeyError`, so `builtin?` doesn't apply and `:open`/`:closed` handle it.
  - Under `:reraise`, `invoke/4` unwraps a `GuardError` and re-raises or re-exits the original
    with its stacktrace, so the default behaviour is unchanged.
  - The return-shape `ArgumentError`s (`semantic_scope.ex:66-69,89-92`) stay outside
    `call_host/3`, so they still raise.
- Update the moduledoc lines at `guardrails.ex:43-59` and `semantic_scope.ex:22-25`.
- Tests: for `:open` and `:closed`, a classifier that exits `{:timeout, {GenServer, :call, _}}`,
  raises `KeyError` and throws all give `{:ok, v}` / `:guard_error`. A plain guard module that
  exits does the same. The test at `guardrails_test.exs:149-164` stays green.
- Optional `:timeout` (Q3): if set, run `do_check` in `Task.async` and call `Task.yield ||
  Task.shutdown`; expiry goes through `on_error_result(policy, mod, {:exit, :timeout})`. With no
  default nothing changes.

**SEC-7**
- In `Memory.run/2`, after `namespace!/2`: if `namespace` equals any mount's namespace, raise
  `ArgumentError`:
  `"memory tool: tool_context[#{inspect(key)}] equals the namespace of mount #{mount}; a session namespace must differ from every mount's"`.
  It names the mount path, not the namespace, so the model never sees the namespace. The check
  is O(mounts) and makes no store call.
- In `validate_mounts!/1`, raise when two mounts share a namespace with different access. Q6
  asks whether to reject any shared namespace.
- Moduledoc: never build a namespace from a user-controlled string without a fixed prefix.
- Tests: the Surprise 8 probe as an assertion (the `create` is refused and the KB is unchanged);
  a `Memory.new/1` duplicate-mount case added to `memory_test.exs:24-40`.

**SEC-8**
- Per the recommendation: Option C (`ConfigTemplate.check_loaded!/1` called at `server.ex:449`
  and in `rebuild/3`, one `plain_data?/1`, behaviour checks, an optional supplement `:pinned`)
  and Option A (docs).
- Tests:
  - a template whose `tool_context` holds a fun raises naming `:tool_context`;
  - a policy ref whose module is not a `PolicyEngine` raises naming `:policy`;
  - with `pinned: [:policy]`, a template carrying `AllowAll` raises;
  - the 1.x fixture still rebuilds.

**SEC-9**
- Add `handle_message/4` `(config, message, carrier, opts)`, validated with
  `Options.validate!(opts, schema, {__MODULE__, :handle_message, 4})`. `/2` and `/3` delegate
  with `[]`. Options:
  - `max_text_bytes`: `{:or, [:pos_integer, nil]}`, default `100_000` (Q5). Summed per part
    before joining. Over the limit gives `{:error, :too_large}`, never logged as an error, with
    stop `error_type: :too_large`.
  - `tool_context`: `{:custom, Normandy.Options, :plain_map, []}`, default not set. When given,
    it **replaces** `config.tool_context` for this call.
- Moduledoc: authentication, authorization and the body limit belong to the host's Plug; every
  caller that gets through reaches every tool in `config.toolset`; for tenancy use
  `tool_context:` per caller.
- Update `telemetry.ex:182-183` (`:too_large`).
- Tests:

    receives no `:converse`;
  - two calls with different `tool_context:` get different `ctx.values` (ContextProbe);
  - `handle_message/4` with an unknown option raises `ArgumentError`.

## Questions for Q

1. **SEC-2: required prefix or opt-out.** There is no server name to default to (Surprise 1).
   - (a) `:prefix` required, with `prefix: false` as an explicit opt-out.
   - (b) Required, with no opt-out.
   - (c) Optional, defaulting to `"mcp"`. That gives a namespace, but two servers then collide
     (`{:tool_name_taken, _}`) and `"mcp__*"` covers every server.

   **Recommend (a).** Every upgrading host has to make a choice and so sees Surprise 2.
   **If wrong:** (a) costs one keyword per call site for hosts that never use policy rules.
2. **A2A tool names** come from the remote card (Surprise 11). Should `A2A.Registry` get the
   same required `:prefix`, in this task or in a follow-up? **Recommend** recording it as a
   SEC-2 sibling and adding `:prefix` to `AgentTool.new/3` (replacing the fixed `"a2a"`) in this
   task, since 2.0 is the breaking window. **If wrong:** A2A keeps the hole SEC-2 closes for MCP.
3. **SEC-4 "timeouts".** Catching exits covers a timeout *raised inside* a guard. Should
   guardrails also get an optional per-guard `:timeout` that runs the check in a task?
   **Recommend:** catch exits and throws now; add `:timeout` only if Q wants it. It has no
   default, but costs a process per guard when set, and context and `$callers` crossing.
   **If wrong:** a guard that blocks without its own timeout still hangs the turn.
4. **SEC-8: A, B or C.** **Recommend A + C** (with the supplement `:pinned`); B is deferred and
   recorded in Known limits. B adds about 2-3 days and still leaves turn state and history
   unprotected unless it is extended to the store contract.
5. **SEC-9 defaults.** Should `max_text_bytes` default to `100_000` (to match decision 12a) or
   to `nil`, which means off and so is not a breaking change? And should `:tool_context`
   replace or merge? **Recommend `100_000`, replace.** Replace is explicit and doesn't leak a
   shared namespace key the host forgot to override. **If wrong:** a host that relies on
   >100 KB A2A prompts gets `:too_large`.
6. **SEC-7 mounts.** Should every pair of mounts with the same namespace be refused, or only
   pairs with different access? **Recommend refusing different access only.** Two read-only
   views of one KB are legitimate.
7. **SEC-13.** Should we refuse `{`/`}` in session ids (non-breaking for normal ids), or
   base64-encode inside the Redis tag (a key-format change that orphans live Redis sessions
   unless migrated)? **Recommend refusing.**
8. **SEC-15 fingerprint and SEC-14.** **Recommend** no fingerprint (document it instead), and
   SEC-14 stays in Task 6.5. Confirm both, so plan-wave-5 lists them as not closed here with
   that reason.
