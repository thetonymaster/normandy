## 0. Surprises (read first)
1. **A template does NOT persist tools.** `ConfigTemplate.from_config/2` (config_template.ex:51-76) stores no tool data; `rebuild/3` takes `tool_registry: supplement.tool_registry` (:157) from the node-local `AgentTemplate` supplement (agent_template.ex:17-18, `required(:tool_registry)`). `@data_fields` has `:tool_context` only. So the plan.md acceptance "a 1.x template that references a removed tool module raises ArgumentError naming the module + MIGRATING §tools" has no persisted carrier. The only places a removed module can show up: (a) the supplement's `tool_registry` being a `%Normandy.Tools.Registry{}` struct (module deleted by the rename) or holding structs whose module only has `defimpl BaseTool`; (b) `Toolset.register/3` receiving such a struct. Plan must pick: validate in `ConfigTemplate.rebuild/3` (check `supplement.tool_registry` is `%Toolset{}`, else ArgumentError naming `inspect(mod)` + "MIGRATING-2.0.md §tools") and in `Toolset.register/3` (module must implement `Normandy.Tool`). Need Q's confirmation of this reading.
2. **`Normandy.Tool` is a behaviour but today's contracts are protocols dispatched on the struct.** `Metadata.tool_description/1` (telemetry/metadata.ex:93-99) uses `BaseTool.impl_for/1`; A2A.Server uses `BaseTool.tool_name/1`; Executor uses `ContextualTool.impl_for/1`. All must switch to module callbacks (`tool.__struct__.name(tool)` or similar). Name/description/input_schema callback shapes are not fixed by the target spec (only `run/2` and `input_schema/1`): `tool_name`, `tool_description` need a home (callbacks `name/1`, `description/1`?).
3. **Policy gets the prepared tool.** `Config.to_pipeline/1` policy_fn passes `tool: tool` (config.ex:78-80) = the prepared (input-merged) struct. After the change `prepared` is the unchanged registered struct plus validated input must travel separately. `PolicyEngine` rules only match tool-name globs (policy_engine.ex), so no rule reads input fields today, but custom engines may. `Dispatch.classify` verdicts `{:execute, prepared, call}` / `{:needs_approval, prepared, call, info}` carry `prepared`; the new shape needs to carry `validated_input` (or put it into the %Context{} later). Turn.Server and tests destructure these tuples.
4. **Timeouts are already read from the struct** (`Map.get(tool, :timeout)`, executor.ex:179) but SEC-1's `:timeout` overwrite works only because `prepare_tool` does `struct(tool, ...)`. `AgentTool` has a `timeout` field that is BOTH its poll deadline AND the Executor timeout; `MCP.ToolWrapper` has none (default 30s).
5. **Three `Task.async_stream` sites + Turn.Server's execute_approved re-derive `prepared`** by calling `Dispatch.prepare_tool` (turn/server.ex:1553). It is the only caller outside Dispatch. After removal, approved calls must re-derive validated input (re-validate from `call.input`, deterministic) or park it.
6. Existing doc comment bug in dispatch.ex:221-239: duplicated `{:needs_approval...}` bullet.
7. Four example Mix apps under `examples/` use `defimpl BaseTool` (separate mix projects, depend on normandy; not in root `mix test`). `test/tools/examples_test.exs` tests `lib/normandy/tools/examples/*` (5 modules shipped in lib; DX-25 says move them out of lib, separate task).
